# Интервалы задач и встреч

Один внешний формат для задачи и встречи: `datetime` — начало, `end_time` —
явно заданное окончание. Оба значения — ISO 8601 с UTC/смещением; внутри моделей
и PostgreSQL они нормализуются к UTC. Конец строго позже начала. Без конца
длительность неизвестна и не назначается автоматически.

```json
{"event_type":"task","name":"Подготовить доклад",
 "datetime":"2026-10-30T15:00:00+03:00","end_time":"2026-10-30T17:00:00+03:00"}
```

В модели Task начало хранится в due_at, конец — в ends_at; в таблице events это
scheduled_at и ends_at. Для задачи без конца due_at сохраняет прежний смысл
точного срока. Срок DATE остаётся отдельной возможностью и не сочетается с концом.
У напоминания по-прежнему один момент remind_at, конец не принимается.

При изменении только начала известная длительность сохраняется. Явно заданное
новое окончание заменяет прежнее. Перевод задачи на срок DATE очищает оба момента.
Передача только нового конца требует уже существующего точного начала.

Для PostgreSQL интервалы задач (режим task_period=due) и встреч видны во всех
периодах, которые они пересекают: `start < period_end AND end > period_start`.
Полуинтервалы: запись, закончившаяся ровно в начале дня, в этот день не попадает.
Одиночные моменты продолжают отбираться по началу. Фильтр задач по времени создания
при прямом task_period=created_at не изменён. Redis-прототип сохраняет конец в JSON,
но его списки, как прежде, фильтруют только created_at.

Обновление данных и результата операции атомарно. Конец входит в отпечаток создания:
повтор с другим концом конфликтует. Миграция 0004 изменяет CHECK без переписывания
данных; downgrade запрещён, пока есть задачи с интервалом.

DTO и REST возвращают end_time также для task. Клиенты должны показывать оба момента
в локальной зоне, включая дату окончания при переходе через полночь. Сортировка
по длительности пока остаётся возможностью встреч.
