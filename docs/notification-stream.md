# Контракт уведомлений backend → MAX, версия 1

Этот документ задаёт транспорт уведомлений, а не клиент MAX и не планировщик.
Backend публикует готовый текст. Компонент команды MAX получает его, разрешает
получателя и отправляет через свой транспорт. Существующие модели Task, Meeting,
Reminder не меняются: создание Reminder само по себе ничего не публикует.
Данные уведомления и результаты его доставки разделены.

Реализованы envelope `Notification` (`app/workers/notification.py`) и Redis-
примитивы публикации/фиксации результата (`app/storage/notification_stream.py`).
Production-потребителя здесь нет. `tests/notification_consumer.py` — одношаговый
стенд с подставной отправкой, только для интеграционных тестов и демонстрации.
Он не запускается при импорте, не является дополнительной production-службой
и не должен развёртываться вместо компонента MAX. Команда MAX подключает этот
контракт к своему процессу; новый процесс поверх согласованной архитектуры
не вводится.

## Имена и формат

| Назначение | Redis Stream |
| --- | --- |
| Вход MAX | `it-gorky:v1:notifications:max` |
| Результаты и промежуточные ошибки | `it-gorky:v1:notifications:results` |
| Dead-letter: окончательно не обработанные | `it-gorky:v1:notifications:dead` |

Все строки UTF-8; Redis-клиент использует `decode_responses=True`.
Redis Stream ID обозначает конкретную публикацию, UUID — логическое уведомление.
Заданный backend `notification_id` сохраняется при повторной обработке.
Поля входного сообщения — отдельные пары field/value, не pickle и не JSON-строка:

| Поле | Значение |
| --- | --- |
| `version` | Строка `1`. Неизвестная версия не отправляется, переносится в dead-letter. |
| `notification_id` | UUID в стандартном строковом представлении. |
| `owner_id` | Непустой внутренний идентификатор владельца из доверенного backend. |
| `text` | Непустой после проверки `strip()` текст, максимум 4000 символов; исходные пробелы сохраняются. |
| `created_at` | Aware ISO 8601; publisher нормализует к UTC. Это время подготовки уведомления, не время Stream ID. |

4000 — ограничение **этого контракта**, не утверждение о лимитах MAX API.
Команда MAX проверяет реальные ограничения своего транспорта. Адрес получателя
берётся из доверенного соответствия owner_id → MAX-пользователь/чат, а не из
инструкций внутри text. Redis — внутренний транспорт, а не публичная авторизация;
текст и owner_id из произвольного браузерного запроса не становятся доверенными.

```python
from datetime import UTC, datetime
from uuid import UUID
from app.storage.notification_stream import NotificationStream
from app.workers.notification import Notification

async def publish(client):
    return await NotificationStream(client).publish(Notification(
        notification_id=UUID("e78b9359-a1f0-4dd5-bd62-1b3494050bc8"),
        owner_id="user-42", text="Пора позвонить Ивану",
        created_at=datetime(2026, 10, 22, 8, tzinfo=UTC),
    ))
```

## Consumer group и чтение

Основная группа: `max-delivery-v1`. Все экземпляры MAX-потребителя используют
**одну** группу, каждый — уникальное имя consumer, например имя экземпляра и
UUID запуска. Отдельная группа на каждый процесс приведёт к рассылке каждой
записи всем группам. На старте `XGROUP CREATE ... max-delivery-v1 0-0 MKSTREAM`;
игнорируется только BUSYGROUP. Старт с `0-0` сохраняет возможность обработать
уведомления, опубликованные до создания группы; `$` здесь использовать нельзя.

Новые сообщения: `XREADGROUP GROUP max-delivery-v1 <consumer> COUNT ... STREAMS
it-gorky:v1:notifications:max >`. `NOACK` запрещён. В production небольшие batch
и `BLOCK` должны укладываться в настроенный командный таймаут Redis (сейчас 2 с;
например, BLOCK 1000 мс). Стенд читает одно сообщение без блокировки.
Полученная запись находится в PEL до терминальной обработки.

## Результат, ошибки и ACK

MAX-потребитель после **подтверждённого успешного ответа своего API** сообщает
`status=delivered`, `outcome=delivered`, по возможности `external_message_id`.
Это подтверждение принятия отправки API, не доказательство чтения человеком.
При временном отказе — `retrying/retryable_failure`; при неопределённом сетевом
исходе — `retrying/unknown`. При окончательном отказе или исчерпании бюджета —
`dead_lettered` с исходным outcome. Ошибки классифицирует MAX-компонент;
сырой текст исключения, токен или HTTP-заголовки в error_code не передаются.

В `results` записываются поля `version=1` и `data=<JSON>`. JSON содержит:

- `notification_id`, `owner_id`, `source_id` (исходный Stream ID);
- `consumer`, `delivery_count` (число получений из PEL);
- `status`: `delivered`, `retrying` или `dead_lettered`;
- `outcome`: `delivered`, `retryable_failure`, `permanent_failure`, `unknown`
  или `not_attempted` (не делали очередную отправку);
- `error_code`: безопасный код до 64 символов `[a-z0-9_]`, либо пустая строка;
- `external_message_id`: строка, если известна, иначе пустая;
- `recorded_at`: время фиксации результата в UTC.

У некорректного входного envelope notification_id/owner_id результата равны
null; корреляция идёт по source_id, оригинал сохраняется в dead-letter.
При переносе в `dead` создаётся такое же событие `version/data`, дополненное
`envelope` — всеми исходными field/value для разбора ошибки.
`dead_lettered` значит «автоматическая обработка остановлена», а не обязательно
«сообщение точно не отправлено»: outcome=unknown сохраняет неопределённость.

ACK выполняется **только после записи результата**:

| Ситуация | Действие с PEL |
| --- | --- |
| Подтверждённая отправка | Записать delivered и XACK атомарно. |
| Временная ошибка, бюджет остался | Записать retrying, оставить pending. |
| Постоянная ошибка, неверная версия/формат или бюджет исчерпан | Записать результат и dead-letter, затем XACK атомарно. |
| Сбой записи результата | Не ACK; восстановление через pending. |

`NotificationStream.report` реализует эту Redis-часть одним Lua-вызовом.
Он не вызывает MAX. Перед записью проверяются consumer и delivery_count
текущей PEL-записи. Устаревший обработчик получает `StaleDeliveryError` и не
может подтвердить перехваченную попытку. Повтор терминального report после
успешного ACK возвращает False и не дублирует результат. Промежуточные события
retrying могут повторяться; обработчик результатов должен учитывать source_id
и delivery_count. Отдельный backend-обработчик результатов в этом блоке не создан.

Короткий `REPORT_RESULT` в `app/storage/notification_stream.py`, по строкам:

| Строка | Действие |
| --- | --- |
| 1 | XPENDING для данного source_id и группы. |
| 2 | Уже нет pending — вернуть 0 без записи. |
| 3 | Consumer/счётчик изменились — вернуть -1 без записи. |
| 4 | Начать проверку двух выходных ключей. |
| 5 | Получить тип ключа. |
| 6 | Отклонить неверный тип до всех изменений. |
| 7 | Закончить проверки. |
| 8 | XADD результата. |
| 9 | Проверить необходимость dead-letter. |
| 10 | XADD оригинала и причины в dead-letter. |
| 11 | Закончить ветку dead-letter. |
| 12 | XACK только для терминального результата. |
| 13 | Вернуть успех. |

KEYS — вход, результаты и dead-letter; ARGV — группа, source_id, consumer,
delivery_count, status, JSON результата, JSON dead-letter. Это standalone Redis;
Cluster и rollback произвольных runtime-ошибок Redis не предполагаются.

## Зависшие сообщения и бюджет попыток

Потребитель восстанавливает pending через `XAUTOCLAIM` в **той же группе**.
`min-idle-time=60000` мс, небольшие batch (стенд — COUNT 10). Возвращённый
курсор нужно сохранять и продолжать с него; пустая порция при ненулевом курсоре
не означает конец PEL. После `0-0` следующий проход начинается заново позднее.
Не удалять consumer с pending и не пересоздавать группу для «починки» очереди.

Внешняя попытка имеет таймаут до 20 с, меньше lease 60 с. Отмена/таймаут не
доказывают, что API не выполнил отправку. Минимальная задержка retry задаётся
idle PEL от последнего чтения/claim, а не локальным sleep: повтор не раньше
60 с после последнего получения записи. Стенд принимает `min_idle_ms=0`
**только для детерминированных тестов**, без ожидания минуты.

Лимит — 3 получения для внешней обработки: `times_delivered` из XPENDING,
увеличиваемый чтением/claim. Это консервативный бюджет: падение до отправки тоже
расходует получение. На третьем неуспехе — dead-letter+ACK. Если три обработчика
упали без отчёта, следующая claim может иметь счётчик 4: её нужно окончательно
зафиксировать с `outcome=not_attempted`, `error_code=attempts_exhausted`,
**не выполнять четвёртую отправку**. Повторная публикация/пересоздание группы
сбрасывают этот бюджет и не должны использоваться для автоматического retry.

Неверный envelope и постоянный отказ переходят в dead-letter сразу. Разбор и
ручной повтор dead-letter — отдельная административная операция с учётом
возможной уже состоявшейся отправки. Автоматического dead-letter replayer нет.
Удалённые pending payloads, возвращаемые XAUTOCLAIM отдельно, требуют тревоги
и восстановления из долговечного источника; стенд останавливается с ошибкой.

## Ограничения доставки и хранения

**При сбое после внешней отправки и до фиксации результата/ACK возможна повторная
доставка. Один Redis Stream эту проблему не устраняет.** Проверка PEL-владельца
защищает Redis-ACK от устаревшего обработчика, но не отменяет внешний HTTP-запрос.
Тест специально воспроизводит две подставные отправки одного notification_id.
Без поддерживаемой внешним сервисом идемпотентности или надёжной сверки результата
exactly-once внешней доставки не обещается; поддержку такого механизма MAX
этот контракт не предполагает.

Публикация выполняется обычным XADD. Повтор публикации после потерянного ответа
может создать вторую Stream-запись того же notification_id. UUID нужен для
корреляции, сам по себе не является реализацией дедупликации. Здесь нет
атомарного outbox с бизнес-операциями или producer-dedup; future dispatcher
должен решить эту границу отдельно. Повтор доставки не вызывает создание
задачи/встречи/напоминания заново.

TTL и автоматический MAXLEN/TRIM **не установлены**: нельзя удалить pending
payload или неразобранный dead-letter только по возрасту. XACK очищает PEL,
но не удаляет запись потока. История и backlog растут; нужны наблюдение и
согласованная очистка с учётом всех групп, архива и горизонта retry.
Результаты/dead-letter могут содержать персональные данные — доступ только
компонентам системы, без вывода текстов в логи. Сохранность Redis зависит от
persistence/тома/backup; текущий Compose без persistence не даёт сохранности
при перезапуске. Stream не заменяет долговечный outbox и резервное копирование.

## Интеграционный стенд

```bash
RUN_REDIS_INTEGRATION=1 uv run --locked --env-file .env pytest -q tests/test_notification_stream.py
uv run --locked --env-file .env python -m tests.notification_consumer
```

Вторая команда выполняет **одну** подставную отправку, без MAX. Использует
уникальный префикс `it-gorky:demo:<UUID>`, печатает только Stream ID и pending,
удаляет только свои три ключа и закрывает клиент. Не запускать как production-
worker. Тесты используют `it-gorky:test:<UUID>` и тот же принцип очистки.

Проверяются публикация до создания группы, чтение, результат и ACK, повторный
report, claim и устаревший consumer, временные/постоянные ошибки, лимит,
падения до обработки, неверная версия, сбой записи результата и окно дубля.

Официальные источники: [XACK](https://redis.io/docs/latest/commands/xack/),
[XAUTOCLAIM](https://redis.io/docs/latest/commands/xautoclaim/),
[redis-py 8.1 команды](https://redis.readthedocs.io/en/v8.1.0/commands.html).
