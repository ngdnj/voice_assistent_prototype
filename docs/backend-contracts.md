# Граница backend и внешних адаптеров

Этот документ фиксирует минимальные правила будущих прикладных операций в
`app/planner/`. Сейчас реализованы модель `Task` и синхронное создание
в памяти: `create_task(owner_id=..., title=..., created_at=...)` в
`app/planner/task.py`. По текущему требованию начальный статус — `active`;
прежний `todo` остаётся целевым статусом Mini App, соответствие ещё не определено.
Внутреннее поле `title` соответствует внешнему `name`. Контекст операции,
PostgreSQL-хранение и полный набор ошибок ниже ещё не реализованы;
модель отклоняет неверные значения через `ValueError`.
Прикладной `TaskService` в `app/planner/service.py` получает явно репозиторий
и часы: `Callable[[], datetime]`. Его async-метод `create_task(owner_id, title, operation_id)`
создаёт модель и ожидает `repository.add(task)` перед возвратом результата;
`get_task(task_id, owner_id)` возвращает `Task | None`.
Здесь имена аргументов приведены для краткости: вызовы используют именованные параметры.
Протокол `TaskRepository` в `app/planner/repository.py` содержит
`async add(task: Task, *, operation: CreationOperation | None = None) -> Task` и
`async get(*, task_id: UUID, owner_id: str) -> Task | None` и
`async list(query: RecordQuery) -> list[Task]`.
Аналогичный метод list добавлен в протоколы встреч и напоминаний.
Сервисы предоставляют `list_tasks`, `list_meetings`, `list_reminders`.
Правила владельца, периода, поиска и страниц, а также обязательный backfill
старых Redis-записей описаны в [record-queries.md](record-queries.md).
Репозиторий обязан фильтровать владельца: чужая и отсутствующая задача
одинаково возвращают `None`. Ошибки репозитория сейчас передаются без перехвата;
Redis-адаптер преобразует ошибки инфраструктуры и повреждение записи в
`TaskStorageError`, а конфликт UUID — в `TaskAlreadyExistsError` (подкласс
`TaskStorageError`). Эти исключения объявлены рядом с протоколом и не зависят
от Redis. Полный набор ошибок из раздела ниже пока остаётся целевым.
`InMemoryTaskRepository` в `app/storage/memory.py` — только тестовая/демонстрационная
реализация, без сохранности после перезапуска. Другой адаптер реализует тот же
протокол без изменения сервиса и правил модели. Уже доступен
`RedisTaskRepository` в `app/storage/redis_tasks.py`: временное основное
хранилище прототипа с JSON, `SET NX` и без TTL. Конструктор модели принимает
сохранённый UUID для восстановления; обычное создание генерирует новый.
Пример запуска и ограничения сохранности приведены в
[README](../README.md).
Документ дополняет
[архитектуру](ARCHITECTURE.md) и [C4](C4.md), не меняя принятые границы проекта.

## Поток данных и ответственность

```text
Внешние данные → адаптер → прикладная операция → результат → адаптер → ответ
```

Адаптер MAX, MCP, HTTP или другого транспорта:

1. Проверяет подлинность источника и устанавливает доверенного владельца.
2. Преобразует внешний формат в явные данные операции и контекст вызова.
3. Вызывает прикладную операцию, сохраняя идентичность действия при повторе.
4. Преобразует результат или ошибку в ответ своего транспорта.

Прикладная операция проверяет бизнес-правила и доступ владельца, выполняет
действие через границу хранения и возвращает данные результата. Например,
`create_task` проверяет непустое название после удаления крайних пробелов,
допустимость срока в будущем полном контракте. Текущая модель не имеет срока
и устанавливает начальный статус `active`.
Эти правила не дублируются в адаптерах. Результат не содержит HTTP-кодов,
сообщений MAX, MCP-объектов или ORM-объектов; пользовательскую формулировку
готовит вызывающая сторона. В целевой прикладной операции успех означает
сохранение записи; текущая функция создаёт только объект в памяти.

Новый адаптер подключается через то же преобразование входа и результата;
правила создания задач в `planner` остаются общими. Внешний MCP-инструмент
`create_event` сохраняет своё имя: для типа `task` его адаптер сможет вызвать
внутреннюю операцию `create_task`.

## Доверенный контекст и идентификаторы

Реализована Redis-идемпотентность создания: обязательный `operation_id` в
сервисе (аналог прежнего `action_id`), область владельца **и типа операции**,
нормализованные данные и возврат исходного результата.
`get_created(owner_id=..., operation=...)` проверяет уже сохранённое действие;
`add(record, operation=...)` атомарно записывает модель, индекс и результат.
Без метаданных add остаётся низкоуровневым неидемпотентным импортом/примером.
TTL у результатов операций не установлен. Детали и построчное объяснение Lua:
[idempotency.md](idempotency.md). Следующие упоминания PostgreSQL — целевой
долговечный вариант, а не текущая реализация.

Владелец передаётся отдельно от пользовательских полей задачи. Backend **не
подтверждает личность по произвольному полю `user_id`** из JSON, текста или
аргументов модели. Доверенный адаптер устанавливает внутренний `owner_id`
после проверки источника; одного названия поля или наличия значения недостаточно.
Непроверенный вызов отклоняется на границе адаптера до выполнения операции.
Прикладной слой использует этот контекст для проверки прав, а хранилище
ограничивает обращения владельцем.

| Значение | Назначение | Поведение при повторе |
| --- | --- | --- |
| `request_id` | Связать логи и диагностику запроса; не является доказательством личности или ключом защиты от дублей | Может сохраняться для исходного запроса; новый транспортный запрос может иметь другой ID |
| `action_id` | Идентифицировать одну логическую операцию; это идентификатор операции, принятый в общей архитектуре | Сохраняется при повторной доставке, retry и повторном tool call того же действия |

Один запрос может содержать несколько действий с разными `action_id`.
Действительно новая операция получает новый `action_id`, даже если текст совпал.
Идентификаторы задаёт приложение, а не модель; дедупликация входного события
адаптером не заменяет защиту самой операции от повторного выполнения.

Ключ повторного выполнения — `(owner_id, тип операции, operation_id)`;
`action_id` в прежних схемах обозначает тот же идентификатор логического действия. Первое успешное создание
атомарно сохраняет задачу и результат действия в PostgreSQL. Повтор с той же
операцией и теми же нормализованными бизнес-аргументами возвращает прежний
результат; изменение типа операции или аргументов даёт `operation_conflict`.
`request_id` не участвует в сравнении бизнес-аргументов. Параллельные повторы
также не должны создавать две задачи. Конкретная схема хранения будет определена
при реализации; гарантировать это одной временной блокировкой Redis нельзя.

## Единый подход к ошибкам

Операция возвращает результат либо сообщает типизированную прикладную ошибку.
Точный Python-тип определим при реализации первой операции. Минимальные данные
ошибки — стабильный `code`, безопасное описание причины и при необходимости
имя ошибочного поля. Исключения драйверов и секреты не выходят в адаптер.

| Код | Значение | Действие адаптера |
| --- | --- | --- |
| `validation_error` | Неверные или недостающие данные, например пустое название или время без зоны | Сообщить конкретную причину/запросить уточнение; не повторять неизменённый ввод автоматически |
| `not_found` | Запись не найдена в доступной владельцу области | Сообщить об отсутствии; не раскрывать существование чужой записи |
| `operation_conflict` | Тот же action_id использован с другой операцией/аргументами либо изменение несовместимо с текущим состоянием | Сообщить конфликт; не подменять action_id автоматически ради повторного создания |
| `temporary_unavailable` | Временно недоступна необходимая инфраструктура, например PostgreSQL | Допустим ограниченный retry с backoff и прежним action_id |

Для `create_task` ошибка `not_found` обычно не требуется; категория фиксируется
для единого подхода, без добавления операций чтения. При неопределённом исходе
сохранения нельзя сообщать, что задача точно не создана: повтор проверяет
сохранённый результат по прежнему ключу. Сбой доставки ответа не повторяет
бизнес-действие. HTTP-статусы и форматы ошибок MCP выбирают соответствующие адаптеры.

## Время

### Напоминания: данные и доставка

`ReminderService` (`app/planner/reminder_service.py`) получает явно репозиторий
и часы. `create_reminder(*, owner_id, text, remind_at, operation_id)` проверяет данные,
сохраняет через `ReminderRepository.add`, возвращает `Reminder`.
`get_reminder(*, reminder_id, owner_id)` возвращает доступную запись либо `None`.
Модель — `app/planner/reminder.py`, протокол и ошибки —
`app/planner/reminder_repository.py`, адаптер — `app/storage/redis_reminders.py`.

`remind_at` и `created_at` обязательны и нормализуются к UTC. При создании
`remind_at < created_at` отклоняется через `PastReminderTimeError`; равенство
допускается. Часы вызываются один раз, введённое время не исправляется.
При чтении используется сохранённый `created_at`, а не текущие часы:
уже наступивший срок не мешает восстановлению записи. Ошибка времени не
записывается в репозиторий; адаптер может запросить у пользователя новое время.

Reminder содержит только UUID, владельца, текст, срок и время создания.
Состояние доставки принадлежит отдельному будущему механизму отправок и
не хранится в Reminder. Создание Reminder не создаёт запись доставки и не
публикует уведомление: существование напоминания не доказывает постановку
на отправку или доставку. Отдельный транспорт уведомлений и его результаты
описаны в [notification-stream.md](notification-stream.md); автоматически
к Reminder он не подключён. Реальных отправок MAX и расписания пока нет.

Redis хранит JSON по `<key_prefix>:v1:reminder:<UUID>` без TTL и без перезаписи
(`SET NX`). Неизвестный/чужой ID даёт `None`, конфликт —
`ReminderAlreadyExistsError`, повреждение или недоступность Redis —
`ReminderStorageError`. Отсутствие TTL не гарантирует сохранность при сбое;
действуют описанные ограничения временного основного Redis-хранилища.

### Общие правила и встречи

Создание/получение встреч доступно через отдельный `MeetingService`
(`app/planner/meeting_service.py`) с явно переданными часами и
`MeetingRepository` (`app/planner/meeting_repository.py`). Методы:
`create_meeting(*, owner_id, title, starts_at, ends_at, operation_id)` и
`get_meeting(*, meeting_id, owner_id)`. Владелец приходит из того же доверенного
контекста адаптера. Отсутствующая и чужая встреча дают `None`.

`Meeting` в `app/planner/meeting.py` неизменяема и содержит только `id`,
`owner_id`, `title`, `starts_at`, `ends_at`, `created_at`. Новая встреча получает
новый UUID; сохранённый можно передать при восстановлении. Все три момента
обязательны и нормализуются к UTC, конец строго позже начала. Длительность,
участники и конфликтующие встречи автоматически не вычисляются.

`RedisMeetingRepository` в `app/storage/redis_meetings.py` использует
`<key_prefix>:v1:meeting:<UUID>` (по умолчанию `it-gorky`), JSON без TTL и
атомарный `SET NX`. Он проверяет владельца и целостность всех полей,
возвращает `Meeting` с исходным UUID и временем. `MeetingStorageError`
обозначает ошибку Redis/данных, `MeetingAlreadyExistsError` — конфликт UUID.
Сервис не зависит от Redis; задачи и встречи остаются отдельными моделями.
Redis временно хранит оба типа записей с теми же ограничениями persistence,
тома данных и резервного копирования, что описаны в README.

Общие функции реализованы в `app/planner/time.py`; `Task` использует `to_utc`
для времени создания. Они не зависят от транспорта, Redis или текущих часов.

- Точные моменты внутри backend — timezone-aware `datetime`, нормализованные
  к UTC. Внешнее значение с явным смещением преобразуется в UTC; naive datetime
  отклоняется, а не получает неявную серверную зону. В обмене используется ISO 8601.
- IANA timezone пользователя, например `Europe/Moscow`, передаётся/хранится
  отдельно. Она берётся из доверенного профиля или явной настройки, не из языка.
- Срок только с датой — `date` / PostgreSQL `DATE`, без автоматического
  превращения в полночь UTC. Задача может не иметь срока. Дата и точный момент
  срока взаимоисключающие.
- `created_at` задаёт backend по подменяемым серверным часам в UTC.
  «Завтра» и другие относительные выражения разрешаются до вызова операции
  по исходному `reference_time` и timezone. При повторе временная опора неизменна.

Доступные операции:

| Функция | Контракт |
| --- | --- |
| `to_utc(value)` | Принимает aware datetime, возвращает datetime с `tzinfo=UTC`; naive datetime отклоняется. |
| `local_to_utc(value, timezone_name)` | Принимает явно заданные локальные часы как datetime без tzinfo и отдельное имя IANA-зоны. Это единственная функция для привязки таких часов к зоне. |
| `day_bounds_utc(day, timezone_name)` | Принимает `date`, возвращает UTC-пару `(start, end)` для локальных полуночей данного и следующего дня. |
| `is_in_period(value, start, end)` | Сравнивает aware-моменты в UTC: `start <= value < end`. Пустой или обратный период отклоняется. |

Используется стандартный `zoneinfo.ZoneInfo` и системная IANA-база. Неверная
зона даёт `ZoneInfoNotFoundError` (либо `ValueError` для некорректного формата
имени); замены на серверную зону нет. Среда запуска должна содержать IANA-базу:
новые зависимости в этом блоке не добавлены.

Политика перевода локального времени строгая: обратное преобразование через UTC
проверяет оба варианта `fold`. Нет допустимого момента —
`NonexistentLocalTimeError`, два момента — `AmbiguousLocalTimeError`.
Часы не сдвигаются автоматически. `to_utc` применяет ту же проверку к datetime
с `ZoneInfo`: даже `fold=1` не считается подтверждением выбора. Для точного
момента в повторяющемся часе вызывающая сторона должна передать UTC или datetime
с явным фиксированным смещением. Значения с фиксированным смещением уже задают
момент; его соответствие отдельной IANA-зоне здесь не проверяется.

Границы дня вычисляются независимо, а не прибавлением 24 часов к UTC-началу:
при DST день может длиться 23 или 25 часов. Неоднозначная/несуществующая полночь
любой границы отклоняется теми же ошибками, включая полностью пропущенную дату.
Дата без времени остаётся `date`; передача её вместо момента, или datetime
вместо даты в `day_bounds_utc`, даёт `TypeError`. Интерпретацию «завтра вечером»
и выбор пользовательской зоны выполняет агент/доверенный адаптер.

```python
from datetime import UTC, date, datetime
from app.planner.time import day_bounds_utc, is_in_period

start, end = day_bounds_utc(date(2026, 10, 22), "Europe/Moscow")
assert start == datetime(2026, 10, 21, 21, tzinfo=UTC)
assert end == datetime(2026, 10, 22, 21, tzinfo=UTC)
assert is_in_period(start, start, end)
assert not is_in_period(end, start, end)
```

Основание: [документация Python zoneinfo](https://docs.python.org/3.12/library/zoneinfo.html).

## Redis и независимость операций

Redis обслуживает очередь и временное состояние вокруг прикладных операций.
Его ключи, Streams ID, TTL, блокировки и клиенты не входят в интерфейс
`create_task` и не определяют бизнес-правила. Операцию должно быть возможно
вызвать напрямую из Python без Redis. PostgreSQL остаётся постоянным
хранилищем задач и результатов действий в целевой архитектуре. По текущему
решению Redis временно хранит задачи прототипа. Сохранность зависит от
persistence и тома данных; текущий Compose их не включает. Это не гарантия
отсутствия потерь и не замена резервному копированию. Очередь не реализована.

## Пример будущего вызова

Это иллюстрация контракта, не исполняемый код и не готовые классы. Контекст
получен от доверенного адаптера; дата срока намеренно не содержит времени.

```python
task = await create_task(
    context={
        "owner_id": "user-42",
        "request_id": "req-101",
        "action_id": "action-501",
        "timezone": "Europe/Moscow",
    },
    data={"name": "Подготовить отчёт", "description": "", "date": "2026-10-23"},
)
# Результат после сохранения (ISO-представление дат для наглядности):
# {"id": "task-7", "owner_id": "user-42", "event_type": "task",
#  "name": "Подготовить отчёт", "description": "", "status": "todo",
#  "date": "2026-10-23", "datetime": None,
#  "created_at": "2026-10-21T09:00:00Z"}
```

Повтор с теми же `owner_id`, `action_id` и данными возвращает `task-7` с прежним
`created_at`, даже при другом `request_id`. В реальном Python-контракте дата
будет типом `date`, точный момент — aware `datetime`; сериализация остаётся
ответственностью адаптера. Конкретные DTO, сигнатура функции, реализация
хранения и механика ошибок появятся в блоке первой операции.
