# Граница backend и внешних адаптеров

Этот документ фиксирует минимальные правила будущих прикладных операций в
`app/planner/`. Сейчас в проекте только каркас: `create_task`, типы данных и
ошибки ниже ещё не реализованы. Документ дополняет
[архитектуру](ARCHITECTURE.md) и [C4](C4.md), не меняя принятые границы проекта.

## Поток данных и ответственность

```text
Внешние данные → адаптер → прикладная операция → результат → адаптер → ответ
```

Адаптер MAX, MCP, HTTP или другого транспорта:

1. Проверяет подлинность источника и устанавливает доверенного владельца.
2. Преобразует внешний формат в явные данные операции и контекст вызова.
3. Вызывает прикладную операцию, сохраняя идентичность действия при повторе.
4. Преобразует результат или ошибку в ответ своего транспорта.

Прикладная операция проверяет бизнес-правила и доступ владельца, выполняет
действие через границу хранения и возвращает данные результата. Например,
`create_task` проверяет непустое название после удаления крайних пробелов,
допустимость срока и устанавливает начальный статус `todo`.
Эти правила не дублируются в адаптерах. Результат не содержит HTTP-кодов,
сообщений MAX, MCP-объектов или ORM-объектов; пользовательскую формулировку
готовит вызывающая сторона. Успех создания означает сохранение записи.

Новый адаптер подключается через то же преобразование входа и результата;
правила создания задач в `planner` остаются общими. Внешний MCP-инструмент
`create_event` сохраняет своё имя: для типа `task` его адаптер сможет вызвать
внутреннюю операцию `create_task`.

## Доверенный контекст и идентификаторы

Владелец передаётся отдельно от пользовательских полей задачи. Backend **не
подтверждает личность по произвольному полю `user_id`** из JSON, текста или
аргументов модели. Доверенный адаптер устанавливает внутренний `owner_id`
после проверки источника; одного названия поля или наличия значения недостаточно.
Непроверенный вызов отклоняется на границе адаптера до выполнения операции.
Прикладной слой использует этот контекст для проверки прав, а хранилище
ограничивает обращения владельцем.

| Значение | Назначение | Поведение при повторе |
| --- | --- | --- |
| `request_id` | Связать логи и диагностику запроса; не является доказательством личности или ключом защиты от дублей | Может сохраняться для исходного запроса; новый транспортный запрос может иметь другой ID |
| `action_id` | Идентифицировать одну логическую операцию; это идентификатор операции, принятый в общей архитектуре | Сохраняется при повторной доставке, retry и повторном tool call того же действия |

Один запрос может содержать несколько действий с разными `action_id`.
Действительно новая операция получает новый `action_id`, даже если текст совпал.
Идентификаторы задаёт приложение, а не модель; дедупликация входного события
адаптером не заменяет защиту самой операции от повторного выполнения.

Ключ повторного выполнения — `(owner_id, action_id)`. Первое успешное создание
атомарно сохраняет задачу и результат действия в PostgreSQL. Повтор с той же
операцией и теми же нормализованными бизнес-аргументами возвращает прежний
результат; изменение типа операции или аргументов даёт `operation_conflict`.
`request_id` не участвует в сравнении бизнес-аргументов. Параллельные повторы
также не должны создавать две задачи. Конкретная схема хранения будет определена
при реализации; гарантировать это одной временной блокировкой Redis нельзя.

## Единый подход к ошибкам

Операция возвращает результат либо сообщает типизированную прикладную ошибку.
Точный Python-тип определим при реализации первой операции. Минимальные данные
ошибки — стабильный `code`, безопасное описание причины и при необходимости
имя ошибочного поля. Исключения драйверов и секреты не выходят в адаптер.

| Код | Значение | Действие адаптера |
| --- | --- | --- |
| `validation_error` | Неверные или недостающие данные, например пустое название или время без зоны | Сообщить конкретную причину/запросить уточнение; не повторять неизменённый ввод автоматически |
| `not_found` | Запись не найдена в доступной владельцу области | Сообщить об отсутствии; не раскрывать существование чужой записи |
| `operation_conflict` | Тот же action_id использован с другой операцией/аргументами либо изменение несовместимо с текущим состоянием | Сообщить конфликт; не подменять action_id автоматически ради повторного создания |
| `temporary_unavailable` | Временно недоступна необходимая инфраструктура, например PostgreSQL | Допустим ограниченный retry с backoff и прежним action_id |

Для `create_task` ошибка `not_found` обычно не требуется; категория фиксируется
для единого подхода, без добавления операций чтения. При неопределённом исходе
сохранения нельзя сообщать, что задача точно не создана: повтор проверяет
сохранённый результат по прежнему ключу. Сбой доставки ответа не повторяет
бизнес-действие. HTTP-статусы и форматы ошибок MCP выбирают соответствующие адаптеры.

## Время

- Точные моменты внутри backend — timezone-aware `datetime`, нормализованные
  к UTC. Внешнее значение с явным смещением преобразуется в UTC; naive datetime
  отклоняется, а не получает неявную серверную зону. В обмене используется ISO 8601.
- IANA timezone пользователя, например `Europe/Moscow`, передаётся/хранится
  отдельно. Она берётся из доверенного профиля или явной настройки, не из языка.
- Срок только с датой — `date` / PostgreSQL `DATE`, без автоматического
  превращения в полночь UTC. Задача может не иметь срока. Дата и точный момент
  срока взаимоисключающие.
- `created_at` задаёт backend по подменяемым серверным часам в UTC.
  «Завтра» и другие относительные выражения разрешаются до вызова операции
  по исходному `reference_time` и timezone. При повторе временная опора неизменна.

## Redis и независимость операций

Redis обслуживает очередь и временное состояние вокруг прикладных операций.
Его ключи, Streams ID, TTL, блокировки и клиенты не входят в интерфейс
`create_task` и не определяют бизнес-правила. Операцию должно быть возможно
вызвать напрямую из Python без Redis. PostgreSQL остаётся постоянным
хранилищем задач и результатов действий. Сейчас ни очередь, ни хранение
в этом блоке не реализуются.

## Пример будущего вызова

Это иллюстрация контракта, не исполняемый код и не готовые классы. Контекст
получен от доверенного адаптера; дата срока намеренно не содержит времени.

```python
task = await create_task(
    context={
        "owner_id": "user-42",
        "request_id": "req-101",
        "action_id": "action-501",
        "timezone": "Europe/Moscow",
    },
    data={"name": "Подготовить отчёт", "description": "", "date": "2026-10-23"},
)
# Результат после сохранения (ISO-представление дат для наглядности):
# {"id": "task-7", "owner_id": "user-42", "event_type": "task",
#  "name": "Подготовить отчёт", "description": "", "status": "todo",
#  "date": "2026-10-23", "datetime": None,
#  "created_at": "2026-10-21T09:00:00Z"}
```

Повтор с теми же `owner_id`, `action_id` и данными возвращает `task-7` с прежним
`created_at`, даже при другом `request_id`. В реальном Python-контракте дата
будет типом `date`, точный момент — aware `datetime`; сериализация остаётся
ответственностью адаптера. Конкретные DTO, сигнатура функции, реализация
хранения и механика ошибок появятся в блоке первой операции.
