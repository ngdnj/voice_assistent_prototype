# Текстовый агент: backend → MCP → PostgreSQL

Реализован текстовый путь, в том числе из MAX через AgentBackend. Jobs/outbox,
agent worker и dispatcher остаются следующими блоками. PostgreSQL/MCP и ASR переиспользованы.
Шесть инструментов — из `app/mcp_server/INTEGRATION.md` v6, включая `update_event` и `delete_event`.
Изменение записей: [event-editing.md](event-editing.md).
Выдача и порядок описаны в [chat-lists.md](chat-lists.md).
Правила переноса и времени словами: [meeting-reschedule.md](meeting-reschedule.md).

## Сборка и ответственность

| Файл | Назначение |
| --- | --- |
| `app/agent/agent.py` | Цикл модели и инструментов, уточнение через историю, проверка разрешённых вызовов, ограничения и защита от неподтверждённого успеха. |
| `app/agent/mcp.py` | MCP client по HTTP; доверенные заголовки вне схем модели; проверка настроек и структурированных результатов. |
| `app/agent/tools.py` | Преобразование nullable MCP-схем для GigaChat SDK, не поддерживающего `anyOf`; серверная схема не меняется. |
| `app/agent/time_input.py` | Консервативная проверка, что пользователь указал часы или точную относительную длительность; без них встреча/напоминание требует уточнения. |
| `app/agent/history.py` | История целыми ходами и сохранённый план текущего хода, in-memory для unit-тестов и Redis для локального запуска. |
| `app/agent/__main__.py` | Сборка существующей модели, MCP gateway и Redis-истории; stdin → один ход → текстовый результат. |
| `app/runtime.py` | Существующий lifecycle, Redis pool и обработка SIGINT/SIGTERM. Агент использует тот же клиент. |
| `evals/backend.py` | Настоящие MCP-инструменты и отдельный PostgreSQL для eval; фиксированные часы сценария и очистка собственного владельца. |

Это ручной ограниченный цикл поверх уже установленного LangChain, без нового
универсального framework. SDK FastMCP и GigaChat проверены по закреплённым версиям;
автотест проверяет конвертацию действительных MCP-схем в функции GigaChat без API-вызова.
`T | null` для необязательного поля отображается модели как T: при отсутствии
значения поле опускается, required остаётся прежним. Произвольные Union не сужаются молча.

## Контракт вызова

```python
reply = await assistant.handle(
    trusted_owner_id,
    text,
    chat_id=trusted_chat_id,
    reference_time=received_at,       # aware UTC, неизменно для повторов этого входа
    timezone="Europe/Moscow",         # явная IANA-настройка, не выводится из языка
    operation_id=logical_turn_id,     # сохранить до первого вызова и повторять при retry
    request_id=log_request_id,        # может меняться между попытками
)
```

Адаптер подтверждает личность до вызова. Аргумент `user_id` в Python-интерфейсе
означает доверенный owner, не произвольное поле из текста или браузера.
В модель не передаются owner, action_id или сервисный токен. Дополнительные
контекстные аргументы модели отклоняются; инструменты вне согласованной тройки
не исполняются. Лимиты полей, дат и прав проверяют существующие planner/MCP.

По умолчанию новый вызов без operation_id означает **новый ход** и получает UUID.
Автоматический retry требует явно переданного прежнего operation_id, исходных
text/reference_time/timezone и тех же owner/chat. Другие данные с этим же ключом —
`OperationConflictError`. Новый осознанный пользовательский запрос получает новый ID,
даже если его текст совпадает с предыдущим.

Уточнение — отдельный новый ход в том же диалоге: «Встреча завтра» → «Во сколько?» →
«В 16». Сначала в истории сохраняется вопрос, затем новая реплика видит контекст.
Если модель сама предложила datetime для встречи/напоминания, но пользователь
не указал время, MCP-вызов блокируется и возвращается конкретный вопрос.
Проверка признаков времени не вычисляет дату/час: распространённые часы и длительности
пропускаются, неподдержанные разговорные формулировки требуют уточнения. Признак
сохраняется в плане хода и может наследоваться из непосредственного уточнения,
но не из произвольных старых записей. Бизнес-правила planner/MCP не меняются.
История изолирована по owner и chat. Сброс истории не отменяет уже созданные записи
и не стирает сохранённые результаты повторов.

## Данные и повторное исполнение

1. До обращения к модели сохраняется отпечаток входа.
2. Модель возвращает tool calls; точный план сохраняется в Redis **до** MCP.
3. Action_id строится как UUID5 от owner/chat/operation_id и номера сохранённого
   вызова, а не берётся из ответа модели. Перезапуск воспроизводит тот же план и ID.
4. После MCP сохраняется ToolMessage с результатом. Если ответ потерян после commit,
   повтор выполняет прежний action_id: PostgreSQL возвращает ту же запись.
5. После ответа сохраняется завершённый ход. Повтор такого хода возвращает сохранённый
   ответ без нового обращения к модели или MCP.

Одинаковый успешный `create_event`, повторно предложенный моделью **в одном ходе**,
использует предыдущий результат. Это защита от зацикливания; две намеренно одинаковые
записи создавайте отдельными пользовательскими ходами.

`validation_error`, `unauthorized`, `operation_conflict` и другие ошибки-объекты
возвращаются модели как ошибочные tool results. `temporary_unavailable` и сетевой
сбой прерывают ход, оставляя план для явного ограниченного retry вызывающей стороны.
Скрытого бесконечного reconnect/retry нет. Успешный ответ инструмента не заменяется
успехом при исключении. Guard один раз перепроверяет неподтверждённое «записал»;
если подтверждения всё ещё нет, возвращает честный текст об отсутствии подтверждения.
Это дополнительная защита формулировок, а не доказательство безошибочности LLM.

## Redis и ограничения

Префикс: `it-gorky:v1:dialog:<owner hex>:<chat hex>`.

- `:history` — list завершённых ходов, максимум 20 по умолчанию. В промпт выбираются
  самые новые целые ходы до бюджета HISTORY_MAX_TOKENS; пары call/result не разделяются.
- `:turn:<operation_id hex>` — JSON плана, результатов и счётчиков, без pickle.
- История и turn имеют TTL HISTORY_TTL_S (7 дней). Запись прогресса обновляет TTL turn,
  завершение обновляет TTL истории. Чтение TTL не продлевает. Оценка токенов приблизительная.
- `:lock` — одна активная обработка диалога, NX с владельцем и TTL 90 секунд.
  Снять lock может только владелец, Lua compare-and-delete. Максимальная обработка
  агента — 60 секунд, максимум 10 ответов модели по умолчанию, до 5 вызовов в ответе
  и 20 вызовов за ход. I/O должен уважать asyncio cancellation.

Это **не долговечная очередь заданий**. При потере/истечении Redis-плана автоматическое
восстановление хода больше не гарантируется; таблица PostgreSQL `operations` защищает
повтор прежних action_id, но не восстанавливает исчезнувшую последовательность действий.
Нельзя обещать безопасное перепланирование утраченного хода. Следующий блок должен
перенести долговечное состояние jobs/действий в PostgreSQL и добавить outbox.
Остановка/падение не откатывает уже сохранённую запись и не означает доставку ответа.
Текущий Compose Redis без persistence особенно подчёркивает это ограничение.

Голос здесь не распознаётся. `AgentReply` содержит текст, вызовы с результатами,
token usage, оценку цены и latency. Качество настоящей русской интерпретации нужно
измерять отдельно, а не выводить из тестов со scripted model.

## Локальный запуск

Нужны закреплённые зависимости, Redis/PostgreSQL, MCP-сервер и доступ GigaChat.
Свою `.env` не перезаписывать. В шаблоне добавлен MCP_URL; MCP_SERVICE_TOKEN
должен совпадать у клиента и сервера и содержать не менее 32 символов.

```bash
uv sync --locked
docker compose up -d --wait postgres redis
uv run --locked --env-file .env alembic upgrade head
uv run --locked --env-file .env python -m app.mcp_server
```

В другом терминале, с GIGACHAT_CREDENTIALS и корректным CA bundle:

```bash
printf '%s\n' 'Создай задачу подготовить отчёт на завтра' |
  uv run --locked --env-file .env python -m app.agent \
    --owner-id local-test-user --chat-id local --timezone Europe/Moscow \
    --operation-id 7d05af70-02a8-4be5-98f0-867cbf8db2e9 \
    --reference-time 2026-10-26T09:00:00Z
```

Повтор той же команды — replay. Для нового запроса используйте другой UUID и его
время первого приёма. Для ответа на уточнение — новый UUID, прежний owner/chat.
reference-time в примере — фиксированная опора; для нового запроса поставьте актуальную.
owner из CLI — доверенная локальная тестовая идентичность, это не MAX-аутентификация.
stdout — текст ответа, stderr — безопасные события с идентификаторами. Ошибки
не печатают input, token, DSN или сырые исключения. SIGINT/SIGTERM обрабатываются
существующим runtime, незавершённая работа не получает ложного подтверждения.

`python -m app check/example` пока остаётся старой Redis-демонстрацией; для нового
текстового пути используйте `python -m app.agent`. Объединение production-процессов
и перевод всей сборки на PostgreSQL — следующий отдельный блок.

## Проверки и eval

```bash
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked mypy
uv run --locked mypy app/runtime.py app/__main__.py
RUN_REDIS_INTEGRATION=1 RUN_PG_INTEGRATION=1 \
  uv run --locked --env-file .env pytest -q -W error::RuntimeWarning
```

POSTGRES_TEST_DB должен явно указывать отдельную тестовую БД; Redis — тестовый.
Unit-тесты не обращаются к облачной модели. Интеграционные тесты используют настоящий
MCP HTTP с токеном, PostgreSQL и Redis; модель подставная. В том числе проверяются
уточнение, FTS, период, другой владелец, пропажа ответа после commit, restart/replay,
TTL, отсутствие пользовательского текста/токена в логах и сборка CLI.

Пропуски eval из-за отсутствующего agent удалены. Старые импорты несуществующей
SQLite-подмены заменены настоящими MCP-инструментами и отдельным тестовым PostgreSQL.
Для исторических seeds фиксируется время их создания; действия агента проверяются
от case.now. Выполнение eval на облачной модели — отдельный платный/лимитируемый
прогон, не часть pytest. `--enable-delete` отклоняется: такого MCP-инструмента в MVP нет.

[LangChain messages](https://docs.langchain.com/oss/python/langchain/messages).
