## Как начать новый чат

Скопируй в новый чат:

> Прочитай `AGENTS.md`, `docs/ML_HANDOFF.md` и `docs/ML_TASKS.md`. Сделай чек-лист «Перед началом» из `ML_TASKS.md`, затем возьми задачу **<ID>**. Коммитить не нужно.

### Перед началом (каждый чат)

1. `git fetch --all --prune`, `git log --oneline HEAD..origin/main`, `git branch -r`. Если в `main` что-то новое, сначала скажи пользователю. Слияние — по §4 `ML_HANDOFF.md` (копия → `checkout pyproject.toml uv.lock` → `merge --ff-only` → вернуть extra `demo`).
2. `git status --short`. Чужие незакоммиченные правки — это работа других чатов, их не откатывать.
3. Проверь, что Docker Desktop запущен и `docker compose ps` показывает Redis и PostgreSQL. Если нет — `docker compose up -d`.
4. В таблице «Кто что держит» отметь, что задача взята. Файлы чужой взятой задачи не трогай.

### Общие правила

- Правим только роль 3. Код ролей 1 и 4 (`app/agent`, `tests/fakes`, `tools/`) — только локально, с пометкой `ROLE 1` / `ROLE 4` в коде.
- **Не коммитить и не пушить**, пока пользователь явно не попросит.
- **Eval с GigaChat — только один прогон одновременно на всю папку.** Параллельные прогоны ловят 429 на OAuth и портят цифры. Перед запуском проверь, нет ли процесса `evals.run`.
- **Eval с GigaChat — только по команде пользователя** (оба набора ×3 — около 30–40 минут и ~0,5 млн токенов). После правки `app/llm/prompts.py` предложи прогон и жди «да». Команды, когда пользователь разрешил, сравнивать с §3 `ML_HANDOFF.md`:
  `PYTHONIOENCODING=utf-8 uv run python -m evals.run --repeat 3 --trace` и то же с `--split debug`.
- Проверки перед отчётом: `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy`,
  `RUN_REDIS_INTEGRATION=1 uv run pytest -q --deselect tests/test_runtime.py` (`test_runtime.py` на Windows не работает, см. §4 handoff).
- Платные вызовы (Cloud.ru, Yandex) — только с согласия пользователя и с оценкой суммы. Токены GigaChat предоплачены.
- В конце: отметь задачу ✅ с датой здесь, обнови §2–§3 `ML_HANDOFF.md`, отчитайся по §7 handoff (что изменилось, какие команды реально выполнены, что не проверено).

## T10. Повтор поиска с синонимами ✅ 27.10 (код, eval не прогонялся)

Решение пользователя 27.10: вместо векторного поиска (embeddings + хранение векторов у роли 4 + пересчёт у роли 1, ~1–2 дня) — повтор с синонимами. Поиск остаётся лексическим (PostgreSQL FTS), семантическим его не называть.
- `app/llm/arg_checks.annotate_result`: пустой результат `get_event_by_query` получает `search_hint` — повторить поиск один раз другими словами того же смысла, затем честно сказать «не нашлось». Ключ отдельный от `note` (его вывод списка роли 1 превращает в фразу про задачи без срока).
- `normalize_args` уже убирает из запроса слова типа записи («напоминание интернет» → «интернет»).
- Срабатывает в продукте только с патчем роли 1 (`annotate_result` вызывается после MCP).
- eval: `found()` теперь принимает слово в любом из запросов (после повтора последний запрос — синоним); новые кейсы `search_synonym_call` («созвон» → «Звонок бухгалтеру»), `search_synonym_dentist` («к зубному» → «стоматолог»), `search_synonym_utilities` («квартплата» → «коммуналка»). Проверка: `uv run --env-file .env python -m evals.run -k search_ --repeat 3`.

**Замер 27.10 (только поиск, слитая сборка с патчем роли 1).** Класс search ×3 с первой версией подсказки: holdout 48/48, весь класс 69/75; провалы — 2 новых кейса с синонимами. Причина: `websearch_to_tsquery` требует **все** слова, а модель при повторе меняла порядок тех же слов («бухгалтер созвон») или писала фразы («оплата жилья»). Подсказка изменена: при повторе — ключевые слова и синонимы **через `or`, каждый вариант одним словом** («созвон or звонок or бухгалтер»). После этого (`-k` ×3): `search_synonym_call`, `search_synonym_dentist`, `search_synonym_utilities`, `search_not_found` — 3/3. Цена: `or` расширяет выдачу — на «квартплату» показываются и «Оплатить коммуналку», и «Оплатить интернет». Весь класс search после правки целиком не перепрогонялся.

**Мужские имена в поиске (27.10).** Полный класс search ×3 с подсказкой `or`: 74/75, holdout 48/48; провал `search_meeting_ivan` 1/3. Причина — стеммер PostgreSQL: «Иван» → `ива`, «Иваном» → `иван` (так же Михаил, Роман, Степан), поэтому запрос «Иван» не находит «Встреча с Иваном»; модель то писала «с Иваном» (находит), то «Иван». Решение пользователя — исправить у роли 4: поиск по префиксу основы (`ива:*`, конфигурация `simple`), патч `role4-overlap-and-descriptions.patch`, тест `tests/test_search_prefix_pg.py`. После правки `search_meeting_ivan` и `search_not_found` 3/3 (модель в этот раз писала «с Иваном»; случай «Иван» закрыт тестом).
