# Ответ после сохранения нескольких записей

## Причина прежнего сообщения

Фраза «Действие выполнено, но не удалось сформировать полный ответ» появлялась
в одной ветке агента: закончились разрешённые шаги, итогового текста модели нет,
но хотя бы одна изменяющая операция уже подтверждена инструментом. Она не означала,
что весь запрос выполнен. Ошибки ASR, webhook и PostgreSQL сами по себе эту фразу
не формировали.

В исследованном запросе от 31 октября 2026 были три разных момента: 1, 2 и 3 ноября
в 14:00 Europe/Moscow. «Послезавтра» и «в понедельник» обозначали 2 ноября.
Три записи сохранены; затем модель повторяла уже выполненные вызовы до лимита.
История содержит десять вызовов создания, но только три разных идентификатора:
дубликатов в этом запросе не появилось. Рабочие записи при расследовании не менялись.

## Новое поведение

- Повтор выполненной операции получает `already_applied` и указание не повторять её.
  После двух последовательных повторов без нового результата цикл останавливается.
  Ограничения шагов, контекста и времени сохраняются, бесконечных повторов нет.
- Для сравнения создания внутри одного хода учитываются равные UTC-моменты,
  отсутствующее/пустое описание и крайние пробелы названия. Аргументы MCP при этом
  не переписываются. Разные описания и разные моменты остаются разными записями.
- Список после нескольких созданий строит приложение из `created`/`updated`/`deleted`,
  которые вернул backend. Даты отображаются в зоне пользователя, одинаковые UUID
  не повторяются. Текст модели не может добавить несохранённую запись в этот список.
- Если закончились шаги/контекст или модель завершилась ошибкой после успешного
  сохранения, ответ перечисляет подтверждённое и предупреждает, что выполнение
  всего запроса не подтверждено. Частичный результат не превращается в «всё готово».
- Отклонённые операции не попадают в список сохранённого. Если нужны уточнения,
  уже сохранённые записи показываются перед вопросом.
- Повтор того же operation_id возвращает сохранённый итог, включая частичный,
  без повторного исполнения действий. Новый пользовательский запрос — новый ход;
  это не глобальное устранение одинаковых напоминаний между независимыми сообщениями.

Пример обычного полного ответа для синтетического запроса:

```text
Созданы напоминания:
1) Завтра, 14:00 — Проверить отчёт
2) 2 ноября, 14:00 — Проверить отчёт
3) 3 ноября, 14:00 — Проверить отчёт
```

Если обработка остановлена без подтверждённого завершения всего запроса, внизу:
«Не удалось проверить выполнение всего запроса. Выше — только подтверждённые записи».

## Границы и проверки

Наличие результата MCP служит доказательством записи. При неизвестном исходе
инфраструктурного вызова этот механизм не придумывает запись и не сбрасывает
защиту по action_id. Общая отмена по таймауту и восстановление незавершённого
задания остаются отдельной задачей надёжности jobs/outbox.

Изменены `app/agent/agent.py`, форматирование `app/agent/presentation.py` и правило
перечисления дат в `app/llm/prompts.py`. Схема БД, MAX, ASR и MCP-контракты не менялись.
Регрессии: `tests/test_agent_saved_answers.py` и сценарий в
`tests/test_agent_integration.py` через настоящие MCP HTTP/PostgreSQL/Redis.
Проверены цикл из примера, частичное выполнение, равные UTC-моменты, ошибки модели,
отклонённая запись, уточнение после сохранения и replay без дублей.

Полная локальная проверка: 865 тестов, 386 subtests, без пропусков;
Ruff/format/mypy, Alembic check и `app check` прошли.

Живой GigaChat проверен на сервере в отдельной временной PostgreSQL-БД:
обычный сценарий сохранил три уникальных момента и вернул список; сценарий с
лимитом одного шага сохранил одну запись и показал предупреждение о частичном
результате. Оба replay не выполняли новых вызовов модели и записей. Всего шесть
вызовов модели; ASR и MAX в этом текстовом прогоне не участвовали. Тестовая БД
после прогона удалена. Артефакт: `/home/bot/backups/result-smoke-20261031-713fb7/`.
Локальная живая попытка с ноутбука закончилась ConnectTimeout и не считается pass.
