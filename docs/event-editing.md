# Изменение и удаление записей

Реализовано для задач, встреч и напоминаний в рабочем PostgreSQL backend.
Путь: MAX → AgentBackend → Assistant → MCP → EventService → PostgresEventMutations.
MAX-клиент, ASR и очередь в этом блоке не изменяются. Нужна миграция `alembic upgrade head` (0003).

## Вызовы

`update_event(event_id, name?, datetime?, date?, end_time?)` меняет существующую запись:

- `name` — непустое новое название до 200 символов. Название и время можно изменить вместе.
- `datetime` — начало встречи, время напоминания или точный срок задачи, ISO 8601 с UTC/смещением.
- `date` — срок задачи без времени. С `datetime` одновременно не передаётся.
- `end_time` — только окончание встречи, строго позже её начала.
- Нужен хотя бы один новый параметр. Пропущенные/null значения сохраняют поля; очистка срока
  и окончания в этом блоке не добавлена. ID, владелец, тип, описание, статус и created_at сохраняются.

При новом date прежний due_at задачи очищается; при новом datetime очищается прежний due_date.
Отсутствие времени не подменяется полночью.

Новое начало встречи без end_time сохраняет известную длительность. Неизвестная длительность
не появляется. Перенос на другую дату без нового часа агент вычисляет с прежним локальным часом
в IANA-зоне пользователя. Домен получает точные моменты и не интерпретирует свободный текст.
Перенос напоминания раньше явно переданного времени изменения отклоняется. Переименовать уже
прошедшее напоминание можно; введённое время молча не исправляется.

Успех: `{"updated": EventDTO}`. Старый `reschedule_meeting` сохранён и использует то же правило
переноса `move_meeting`; новые клиенты могут использовать update_event для всех трёх типов.

`delete_event(event_id)` удаляет одну доступную запись. Успех: `{"deleted": EventDTO}`.
По явной просьбе с однозначной записью дополнительного подтверждения не требуется.
При нескольких совпадениях агент показывает варианты и спрашивает, какую запись выбрать.
Код также блокирует произвольный выбор из нескольких результатов текущего поиска, если в
запросе нет единственного полного названия выбранной записи. На уточнение можно ответить новым сообщением.

В обоих вызовах owner_id и action_id приходят из доверенного контекста. Модель не выбирает владельца.
Чужая/отсутствующая/удалённая запись даёт одинаковый `not_found`; неверные поля — validation_error;
конфликт action_id или конкурентное изменение — operation_conflict; сбой хранилища — temporary_unavailable.
Агент подтверждает изменение/удаление только после соответствующего успешного результата.

## Удаление и повторы

Удаление логическое: events.deleted_at заполняется UTC-моментом, запись скрывается из get/list,
FTS, REST Mini App и смены статуса. Это не физическое стирание. Восстановление, массовый endpoint
удаления и автоматическая физическая очистка не реализованы. История действий без TTL сохраняется,
как и прежде; FK операций продолжает ссылаться на запись.

Изменение записи и добавление операции фиксируются одной транзакцией под блокировкой строки.
Повтор action_id с теми же данными не выполняет действие снова. Другие данные/другой тип операции
с прежним action_id дают конфликт. Изменение по устаревшему снимку отклоняется.
Повтор обновления возвращает текущее состояние, не отменяя последующее редактирование.
Повтор удаления возвращает сохранённое удалённое состояние даже через другой экземпляр репозитория.
Повтор старого создания/обновления после удаления даёт конфликт и не восстанавливает запись.
Уже завершённый ход агента может вернуть свой исторический сохранённый ответ без нового действия.

## Файлы и проверки

| Файлы | Ответственность |
| --- | --- |
| app/planner/event_repository.py, event_service.py | Узкая граница хранилища и правила двух операций над существующими моделями |
| app/planner/meeting.py, meeting_service.py | Общее правило переноса для старого и нового вызова |
| app/storage/postgres/event_mutations.py | Владелец, блокировка, сравнение снимка, атомарная запись операции и изменения |
| app/storage/postgres/records.py, tables.py | Скрытие удалённых записей и новое поле хранения |
| migrations/versions/0003_event_mutations.py | Новая колонка и типы операций; старые миграции не меняются |
| app/mcp_server/tools.py, server.py, __main__.py | Контракты, ошибки и сборка EventService |
| app/agent/mcp.py, agent.py, app/llm/prompts.py | Инструменты, стабильные action_id, выбор записи и подтверждения |
| evals/backend.py, cases.py, checks.py, run.py, app/config.py | Настоящий редактор в eval, UUID вместо старых числовых fixtures; флаг выбора delete-сценариев |

Redis-репозитории прототипа не расширяются. REST отражает изменения, но новые маршруты редактирования
для Mini App не добавлены. Новый EventService не заменяет существующие модели и сервисы создания.

Проверки: tests/test_event_service.py; tests/storage_pg/test_event_mutations.py;
tests/mcp_server/ и tests/api_records/; tests/test_agent*.py. Проверяются все типы, поиск и период
после изменения, владельцы, конкурентные повторы, сбой между INSERT операции и UPDATE записи,
неподтверждённые ответы модели и отсутствие восстановления после удаления.

Примеры: «Переименуй встречу про хакатон в Обсуждение проекта», «Перенеси напоминание про аптеку
на завтра в пять вечера», «Поменяй срок задачи отчёт на пятницу», «Удали встречу Обсуждение проекта».
