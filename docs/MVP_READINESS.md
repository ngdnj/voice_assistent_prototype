## 3. Что мешает считать систему рабочим MVP

1. Нет исполняемого `app/agent/agent.py`, MCP client, истории и цикла инструментов.
   В проверенных `main`, `bot` и ML-ветке `app/agent/` содержит только пустой `__init__.py`.
   ML-handoff описывает готовые файлы, но они не находятся в этих Git-снимках.
2. Бот вызывает DemoBackend; пользовательский текст не доходит до сохранения записи.
3. Runtime и MCP используют разные хранилища. CLI пишет в Redis, MCP/REST — в PostgreSQL.
   Без единой сборки нельзя считать данные бота и Mini App общими.
4. Нет долговечных jobs/outbox, worker и dispatcher. В боте `BackgroundRunner` принимает
   coroutine; её нельзя просто сериализовать в Redis. При падении процесса работа теряется.
5. Нет Mini App: ни React/Vite-проекта, ни клиентского пути с initData и REST.
6. Нет приёмочного прогона всей цепочки в MAX, включая реальное голосовое и перезапуск.

Поэтому существующие компоненты не требуется писать заново. Основная работа —
получить отсутствующий агент, соединить контракты и реализовать восстановимую обработку.

## 4. ТЗ по последовательным блокам

### A. Зафиксировать интеграционные контракты

**Ответственные:** backend + MAX + ML + PostgreSQL/MCP.

Сделать:

- Работать от актуальной main; проверить и принять MAX-ветку.
- Запросить у ML-разработчика коммит с описанными `agent`, `tools`, `guard`, `history`.
  Если кода нет, явно зафиксировать реализацию агентского цикла за backend; не считать handoff реализацией.
- Согласовать адаптацию `BackendRequest` бота к агенту и новый сериализуемый контракт приёма jobs.
- Принять PostgreSQL как единственное основное хранилище записей; решить перенос старых Redis-данных.
  Не удалять их автоматически. Redis оставить для состояния, очереди и временного контекста.
- Согласовать единые имена идентификаторов: `request_id`, `source_event_id`, `job_id`,
  `action_id/operation_id`, `notification_id`. Владелец устанавливается доверенным адаптером.
- Зафиксировать область истории: пользователь + диалог/чат; зону брать из явной настройки
  продукта, затем профиля. Не определять её по языку сообщения.

**Готово, когда:** опубликованы вход/выход агента, формат job, ошибки и правила retry;
определён владелец каждого ресурса и этапа. Существующий порт бота не меняется молча.

### B. Собрать первый текстовый путь: агент → настоящий MCP → PostgreSQL

**Ответственный:** backend. **Поставщики:** ML — модель/промпт; роль 4 — MCP и PostgreSQL.

Сделать:

- Подключить существующие LLM и промпт к ограниченному агентскому циклу.
- Ввести MCP client с тремя действующими инструментами; сверить JSON-схемы и ответы
  с `INTEGRATION.md`, а не со старой SQLite-подменой.
- Контекст владельца, зоны, request и action передавать из backend через доверенные заголовки.
  Не давать модели задавать владельца. MCP_SERVICE_TOKEN не включать в промпт.
- Обрабатывать результаты `created/events/error`, в том числе ошибки-объекты,
  а не только исключения. Не сообщать об успехе до подтверждения инструмента.
- При нехватке времени встречи/напоминания задать конкретный вопрос. Ответ на уточнение
  использовать вместе с предыдущим контекстом, не создавать запись заново.
- Ограничить число шагов, общий срок и retry временных ошибок. Хранить историю
  с бюджетом и целыми парами tool call/result; очищать и изолировать по диалогу.
- Сохранять неизменный `reference_time`. Для каждого логического создания сохранять
  action_id, имя инструмента и аргументы до исполнения. Retry использует тот же вызов;
  нельзя заново генерировать ID после очередного ответа LLM.

**Особенность существующих адаптеров:** Redis различает владельца + тип + operation_id,
PostgreSQL — владельца + operation_id, дополнительно сверяя тип и отпечаток.
Новый логический вызов получает отдельный action_id независимо от типа записи.

**Готово, когда:** текст создаёт задачу/встречу/напоминание в PostgreSQL, выбирает период
и ищет запись; уточнение работает; одинаковый повтор не создаёт дубль; чужие записи недоступны.
Начать с локального интеграционного теста без MAX, затем заменить DemoBackend адаптером агента.

### C. Сделать приём и обработку восстанавливаемыми

**Ответственный:** backend; изменения транспорта — совместно с MAX-разработчиком.

Сделать:

- Сохранить входное событие, job и запись outbox в PostgreSQL до подтверждения приёма.
  Уникальность события — по источнику и устойчивому source_event_id.
- Заменить передачу coroutine в `BackgroundRunner` на приём сериализуемого задания.
  В Redis Streams передавать job_id, а не аудиобайты или весь диалог.
- Реализовать agent worker: чтение новых/pending jobs, ограниченные retry,
  сохранение результата, затем ACK. После сбоя продолжать с сохранённого этапа.
- Согласовать busy lock бота со состояниями `processing`, `awaiting_clarification`,
  `completed`, `failed`. Один активный запрос на диалог; ответ на уточнение не блокируется.
- Для голоса хранить проверенную audio_ref и достаточные данные для повторной обработки;
  выбрать, как пережить истечение внешней ссылки. ASR выполняется один раз на успешно
  сохранённом этапе, а не при каждой неудачной отправке ответа.
- Создание записи и запись результата действия атомарны; готовый ответ и исходящий outbox
  сохраняются атомарно между собой. Восстановление не повторяет уже сохранённое действие.
  Не держать транзакцию PostgreSQL во время ASR/LLM/отправки MAX.
- Добавить dispatcher для повторяемой публикации outbox; совместно с MAX-командой
  подключить единственный рабочий потребитель уведомлений по существующему контракту.
  Соответствие owner_id → получатель/чат должно быть доверенным и явно сохранённым.
- Не умножать попытки незаметно: у MaxClient есть собственные retry, у Stream — бюджет
  получений. Согласовать общий предел/20-секундный бюджет внешней попытки.

**Готово, когда:** повтор webhook, падение до/после commit, перезапуск worker и ошибка
MAX не теряют принятое задание и не создают вторую запись. Незавершённое не ACK.
Сбой после внешней отправки до фиксации результата может дать повторное сообщение:
один Stream и дедупликация записи не обеспечивают exactly-once внешнюю доставку.

### D. Собрать процессы и подключить настоящий MAX/голос

**Ответственные:** backend + MAX + ML.

- Расширить текущую точку сборки до трёх процессов: API, agent worker, dispatcher.
  MAX webhook, MCP и REST разместить внутри одного API-процесса, без четвёртого
  постоянного MCP-сервиса. Существующие standalone-запуски оставить dev-утилитами.
- В приложении использовать PostgreSQL-репозитории. Redis не должен быть вторым
  независимым источником записей. Обновить check/example под рабочую сборку.
- Согласовать единственного владельца ASR-этапа: сейчас он выполняется в фоне бота,
  целевой agent worker управляет обработкой. Не распознавать одно аудио дважды.
- Выбрать и проверить один основной ASR. Для GigaAM измерить холодный запуск/RAM/задержку;
  для облачного адаптера проверить доступ и согласованный бюджет. Не устанавливать оба
  варианта в production просто потому, что для них есть адаптеры.
- Проверить нативное голосовое и аудиофайл на реальном MAX. Ограничение пустых событий,
  описанное MAX-командой, пока считать её наблюдением, а не независимо подтверждённым фактом.
  Если актуально — записать воспроизводимый обходной путь и честное ограничение продукта.
- Описать Compose-запуск приложения, миграции, HTTPS, секрет webhook, ASR-зависимости,
  порядок проверки и остановки. На SIGTERM прекратить admission/чтение, ограниченно
  завершить активное, сохранить состояние и закрыть PG/Redis/HTTP/MCP-клиенты.

**Готово, когда:** из чистого checkout по README запускается система, пользователь MAX
посылает текст и голос, получает подтверждение сохранения и может найти ту же запись позже.

### E. Реализовать выбранный Mini App

**Ответственная:** роль 5; backend/MAX/роль 4 помогают подключить существующий REST.

- React + TypeScript + Vite + MAX Bridge: период, вкладки задач/напоминаний/встреч,
  поиск, карточки, смена статуса задачи.
- Передавать исходную initData в `X-Max-Init-Data`, IANA timezone отдельно.
  owner_id не принимать из браузера; подпись проверяет существующий backend.
- Обработать loading/error/empty, 401/404/422/503, отмену устаревших запросов,
  неуспешное обновление статуса. Данные не дублировать в локальном хранилище браузера.
- Добавить запуск/сборку/проверки frontend, публикацию и кнопку открытия из бота.
- Период задач в MCP/REST уже фильтрует **срок**, не created_at; задачи без срока
  в период не входят. Поиск без периода должен позволять найти такие задачи.

**Готово, когда:** созданная ботом запись видна этому же пользователю Mini App;
статус сохраняется на сервере и после повторного открытия; чужие данные недоступны.
Этот блок входит в согласованный объём продукта. Первое рабочее демо бота можно
провести до него, но завершённым согласованным MVP такое демо ещё не является.

### F. Пройти общую приёмку

**Ответственные:** все роли; сценарии и результаты собирает роль 6.

1. Создание задачи без срока и с датой; дата не становится фиктивной полуночью UTC.
2. Создание встречи со временем; без времени — уточнение, без окончания — неизвестная длительность.
3. Создание напоминания на будущий момент; прошлое время не исправляется молча.
4. Выдача за день/неделю и поиск ранее созданной записи, включая пустую выдачу.
5. Уточняющий ответ сохраняет исходный замысел и не создаёт дубль.
6. Те же сценарии для реальной русской речи с датами и именами; показать расшифровку.
7. Два пользователя и два диалога не смешивают данные/историю/блокировки.
8. Перезапуск сохраняет записи; duplicate webhook/tool call не создаёт второй объект.
9. Падение worker/dispatcher и недоступность Redis/PG/MAX не дают ложного успеха;
   доставка повторяется без повторного бизнес-действия. SIGTERM оставляет работу восстанавливаемой.
10. Mini App читает те же записи и сохраняет смену статуса.

Автотесты — с реальными тестовыми PostgreSQL/Redis и fake ASR/LLM/MAX; отдельный
ограниченный smoke — с тестовым ботом и выбранным провайдером. Eval прогнать против
действительного агента и MCP, отдельно от старых оценок прототипа. В ML-handoff
уже перечислены ошибки уточнения напоминания, несуществующей даты и перехода через
полночь; добавить их в регрессионную приёмку, не переносить старый процент качества
на новую систему без измерения.

## 5. Что не должно задерживать основной путь

- TTS: текстовый ответ на голос допустим.
- Доставка напоминаний по расписанию: отдельный следующий блок после создания,
  выборок и поиска. Для него нужны планировщик, состояние доставки и MAX-потребитель;
  нельзя считать его готовым из-за наличия Reminder или контракта Stream.
- Удаление, перенос, повторяющиеся события, участники, приглашения, календари,
  обнаружение конфликтов, embeddings, сложная RBAC и Kubernetes не входят в текущий MVP.
- Полный Grafana-стек не является условием первого сквозного сценария. Существующие
  метрики подключить при общей сборке, структурированные логи сохранить.
