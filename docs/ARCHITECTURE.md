# Архитектура голосового ассистента

## Принятое размещение и границы

Одна кодовая база Python, корневой пакет `app/`. Это размещение заменяет
`backend/src/assistant/` из предыдущего плана; проверки находятся в корневом `tests/`.
Основание — архитектурный план IT Gorky (MD и DOCX), относящаяся к проекту
расшифровка обсуждения и текущее решение о структуре. Остальные требования сохраняются.
Ниже описано целевое поведение; сейчас созданы только пустые пакеты.

| Модуль | Ответственность |
| --- | --- |
| `bot` | Адаптер MAX: разбор событий, нормализация сообщений, безопасное получение аудио, отправка статусов, расшифровок и ответов. |
| `api` | HTTP-маршруты и подключение webhook, проверка входа, REST для Mini App с проверкой initData, подключение MCP к API. |
| `agent` | Управление диалогом, ограниченной историей, уточнениями, вызовами ASR/LLM и MCP client; ограничения шагов и времени обработки. |
| `asr` | Распознавание аудио через адаптер выбранного провайдера; возвращает текст и ошибки. |
| `llm` | Клиенты LLM, промпт/few-shot, преобразование запросов и ответов модели, включая предложенные вызовы инструментов. |
| `tts` | Необязательное преобразование подготовленного ответа в аудио через адаптер провайдера. |
| `planner` | Сущности и операции `task`, `meeting`, `reminder`: проверка полей, владельца, дат, статусов и допустимых изменений. |
| `mcp_server` | Три типизированных инструмента: `create_event`, `get_events_by_period`, `get_event_by_query`; проверка доверенного контекста и вызов planner. |
| `storage` | Реализация доступа к PostgreSQL и Redis, репозитории, транзакции, поиск и хранение состояния. |
| `workers` | Запуск agent worker и dispatcher, обработка/восстановление jobs, публикация очереди, доставка ответов и последующих напоминаний. |
| `tests` | Проверки бизнес-правил, компонентов и интеграций без живых LLM/ASR в unit-тестах. |
| `evals` | Контрольные сценарии ASR и пяти классов запросов: создание, период, уточнение, поиск, общий вопрос. |
| `docs` | Архитектурные решения, контракты, инструкции и результаты проверок по мере разработки. |

Agent управляет сценарием; LLM-адаптер предоставляет доступ к модели.
ASR, LLM и TTS не управляют очередью и не отправляют сообщения в MAX.
Модель предлагает инструмент и аргументы; приложение проверяет и выполняет вызов.
REST и MCP используют одни операции planner, без дублирования бизнес-правил.
Planner не зависит от MAX, FastAPI и AI-провайдеров; конкретный доступ к хранилищу
остаётся в storage. Необходимые границы хранения определим при реализации операций.

## Процессы и данные

Три процесса одного проекта:

1. **API** — HTTP, webhook, REST для Mini App и встроенный FastMCP server.
2. **Agent worker** — получение jobs из очереди и запуск сценария agent.
3. **Dispatcher** — публикация jobs из outbox, доставка сохранённых ответов;
   после основного пути — доставка напоминаний по расписанию.

PostgreSQL хранит постоянные записи, jobs, результаты действий и outbox.
Redis хранит временные историю/состояние/блокировки диалога и очередь Redis Streams.
В очередь передаётся `job_id`. Подтверждение задания происходит после сохранения
результата; долговечные jobs/outbox позволяют восстановить работу после сбоя.
Бот и Mini App читают одни записи PostgreSQL; отдельного хранилища событий в браузере нет.

## Путь одного голосового запроса

Пример: «Напомни завтра в десять позвонить Ивану».

1. API принимает webhook, проверяет секрет и событие. Bot нормализует сообщение
   с пользователем, чатом, идентификатором исходного события и ссылкой на аудио.
   При первом приёме фиксируются неизменяемые `received_at` и `reference_time`;
   timezone берётся из профиля или явной настройки продукта.
2. Приём дедуплицирует событие и сохраняет сообщение, job и outbox в одной
   транзакции PostgreSQL. Только после фиксации API подтверждает webhook;
   распознавание и модель выполняются вне HTTP-запроса.
3. Dispatcher публикует `job_id` в Redis Streams. Agent worker получает задание
   и устанавливает блокировку диалога с владельцем `job_id` и TTL.
   Пользователь получает статус начала обработки через bot.
4. Аудио безопасно загружается адаптером MAX; agent вызывает ASR и получает текст.
   Расшифровка подготавливается к доставке пользователю. Текстовый ввод начинает
   общий сценарий с этого места, пропуская ASR.
5. Agent передаёт LLM текст, ограниченную историю, timezone и временную опору.
   Модель предлагает `create_event` с типом `reminder`. Если обязательных данных
   не хватает, agent сохраняет состояние уточнения и готовит конкретный вопрос;
   ответ пользователя должен приниматься, не оставаясь заблокированным.
6. MCP client агента вызывает MCP внутри API. Сервер проверяет доверенный контекст;
   `user_id`, `request_id`, `action_id` устанавливает приложение, а не модель.
   Planner проверяет поля и права, storage атомарно сохраняет запись и результат
   действия в PostgreSQL. Повтор того же `action_id` возвращает прежний результат;
   несовместимые аргументы отклоняются.
7. Результат инструмента возвращается модели через agent. Подтверждение создания
   формируется только после успешного сохранения. Worker фиксирует ответ,
   завершение job и отправку в outbox, затем подтверждает задание в очереди
   и согласованно освобождает состояние обработки.
8. Dispatcher отправляет сохранённый ответ через bot в MAX. Ошибка доставки
   повторяет доставку, сохраняя результат операции. TTS можно добавить для готового
   ответа; его ошибка не запускает создание записи заново. Напоминание в назначенное
   время доставляется отдельным блоком расписания.

## Сохраняемые правила

Все выборки ограничены владельцем на сервере. Точные моменты хранятся как
`TIMESTAMPTZ`, IANA timezone — отдельно; дата задачи без времени — как `DATE`.
Задача может не иметь срока; встреча и напоминание требуют точного времени.
Относительные даты вычисляются от исходного `reference_time` в зоне пользователя,
включая повторы после полуночи. Периоды — `[start_time, end_time)`.
Статусы задач Mini App: `todo`, `in_progress`, `done`.

Поиск MVP — PostgreSQL FTS с русской конфигурацией и GIN, с фильтром владельца.
TTS, расписание напоминаний, внешние календари и embeddings не блокируют четыре
основных сценария. Каталоги frontend, миграций, конфигурация процессов и внутренние
подпапки будут добавляться при разработке соответствующих блоков.
