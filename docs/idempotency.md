# Идемпотентность создания в Redis

## Контракт и область уникальности

`TaskService.create_task`, `MeetingService.create_meeting` и
`ReminderService.create_reminder` требуют именованный `operation_id` от
доверенного вызывающего адаптера. Это непустая строка до 200 символов;
значение не обрезается и не генерируется заново при retry. Поле не выбирает LLM.
Оно соответствует прежнему понятию `action_id`: одно логическое действие,
а не один сетевой запрос. `request_id` остаётся идентификатором для логов и
не участвует в сравнении данных. Владелец по-прежнему устанавливается адаптером.

Ключ уникальности — `(owner_id, тип операции, operation_id)`. Три типа:
`create_task`, `create_meeting`, `create_reminder`. Один operation_id можно
использовать у другого владельца или для другого типа: это разные операции.

| Операция | Нормализованные бизнес-данные для сравнения |
| --- | --- |
| Создание задачи | `title.strip()` |
| Создание встречи | `title.strip()`, `starts_at` и `ends_at` в UTC |
| Создание напоминания | `text.strip()`, `remind_at` в UTC |

Строки сохраняют регистр и внутренние пробелы: изменение этих значений — другие
данные. Разные UTC-смещения одного момента дают одинаковые данные.
`CreationOperation.from_data` строит SHA-256 от канонического JSON с сортировкой
ключей. UUID и `created_at`, назначаемые сервером, в fingerprint не входят.
`OperationConflictError` означает повтор того же ключа с другими данными;
автоматически менять operation_id после конфликта нельзя.

Сервис сначала проверяет результат операции, затем при его отсутствии создаёт
модель по текущим переданным часам. Поэтому повтор напоминания после наступления
его срока возвращает исходный результат, а не ошибку прошлого времени.
Первое создание с прошлым remind_at по-прежнему отклоняется, ничего не сохраняя.
Ошибки формата времени и operation_id проверяются до обращения к результату.
Невалидные данные без успешно сохранённой операции не резервируют operation_id.

```python
from datetime import UTC, datetime
from app.planner.service import TaskService
from app.storage.redis_tasks import RedisTaskRepository


async def example(client):
    service = TaskService(
        repository=RedisTaskRepository(client),
        clock=lambda: datetime(2026, 10, 22, 8, tzinfo=UTC),
    )
    first = await service.create_task(owner_id="user-42", title="Отчёт", operation_id="message-123:create-1")
    replay = await service.create_task(
        owner_id="user-42", title=" Отчёт ", operation_id="message-123:create-1"
    )
    assert replay == first  # Включая UUID и created_at.
```

## Хранение и атомарная фиксация

Ключ операции:
`it-gorky:v1:operation:create_<тип>:<owner_id UTF-8 hex>:<operation_id UTF-8 hex>`.
Значение Redis string: 64 ASCII-символа fingerprint, перевод строки, затем
исходный JSON результата. Записи и индексы сохраняют прежнюю схему `v1`.
JSON-снимок содержит первоначальные UUID, владельца и все поля модели.

Репозиторий предоставляет `get_created(owner_id=..., operation=...)` и
`add(record, operation=...) -> model`. Предварительное чтение — оптимизация
повтора, не блокировка. Даже если два запроса одновременно не нашли результат,
решение принимает один атомарный `EVAL`: второй получает JSON победителя,
его кандидат с новым UUID не записывается. Никакого окна между сохранением
модели и фиксацией результата на стороне Python нет. Потеря сетевого ответа
после commit лечится повтором **с тем же operation_id**.

Прямой `repository.add(record)` без метаданных оставлен для низкоуровневых
примеров, тестов и импорта: он защищает UUID от перезаписи, но не обеспечивает
идемпотентность операции. Транспортные адаптеры должны вызывать сервис.
Тестовый in-memory адаптер задач соблюдает тот же контракт в рамках одного
процесса/event loop; его данные и история операций не переживают перезапуск.

## Lua: построчное объяснение

Скрипт `CREATE_ONCE` находится в `app/storage/redis_operation.py`, всего 17 строк.
`KEYS[1]` — JSON записи, `KEYS[2]` — индекс её владельца/типа,
`KEYS[3]` — результат операции. `ARGV[1]` — fingerprint, `ARGV[2]` — JSON
кандидата, `ARGV[3]` — элемент индекса `время|UUID`. Все ключи передаются явно.

```lua
local old = redis.call('GET', KEYS[3])
if old then
    if #old < 66 or string.sub(old, 65, 65) ~= '\n' then
        return redis.error_reply('Invalid operation result')
    end
    if string.sub(old, 1, 64) ~= ARGV[1] then return {-1, ''} end
    return {1, string.sub(old, 66)}
end
if redis.call('EXISTS', KEYS[1]) == 1 then return {0, ''} end
local kind = redis.call('TYPE', KEYS[2]).ok
if kind ~= 'none' and kind ~= 'zset' then
    return redis.error_reply('Invalid index type')
end
redis.call('SET', KEYS[1], ARGV[2])
redis.call('ZADD', KEYS[2], 0, ARGV[3])
redis.call('SET', KEYS[3], ARGV[1] .. '\n' .. ARGV[2])
return {1, ARGV[2]}
```

| Строка | Что делает |
| --- | --- |
| 1 | Читает результат; неверный Redis-тип вызывает ошибку до записей. |
| 2 | Если операция уже завершена, переходит в ветку повтора. |
| 3 | Проверяет длину и разделитель сохранённого формата. |
| 4 | Отклоняет повреждённый формат, ничего не создавая. |
| 5 | Завершает проверку формата. |
| 6 | При другом fingerprint возвращает код конфликта `-1`. |
| 7 | При совпадении возвращает исходный JSON с кодом `1`. |
| 8 | Заканчивает ветку повтора. |
| 9 | Защищает существующий UUID кандидата; код `0` означает конфликт записи. |
| 10 | Получает тип индекса до любых изменений. |
| 11 | Проверяет, что индекс отсутствует либо является sorted set. |
| 12 | Отклоняет неверный тип индекса до любых изменений. |
| 13 | Заканчивает проверку индекса. |
| 14 | Сохраняет JSON новой записи. Проверка UUID уже сделана внутри того же EVAL. |
| 15 | Добавляет запись в существующий индекс; score остаётся нулём. |
| 16 | Сохраняет fingerprint и JSON результата без TTL. |
| 17 | Возвращает первоначальный результат успешной операции. |

Redis не обслуживает другой запрос посреди скрипта. После получения JSON адаптер
проверяет его модель, владельца, совпадение с записью и наличие элемента индекса.
Если история операции есть, а данные/индекс потеряны или повреждены,
возвращается `*StorageError`, а не повторное создание. Данные не ремонтируются
автоматически. Lua не обеспечивает откат произвольных runtime-ошибок Redis;
допустимость типов проверяется до изменений. Это один standalone Redis,
не Redis Cluster. [Атомарность Lua в Redis](https://redis.io/docs/latest/develop/programmability/eval-intro/)
не заменяет persistence и резервное копирование.

## Срок хранения и ограничения

**TTL не устанавливается** ни на operation_id, ни на записи, ни на индексы.
Результат хранится бессрочно, пока ключи сохраняются в Redis. Это осознанный
выбор для прототипа: отложенный retry через сутки или неделю не должен создавать
дубль из-за истечения технического TTL. Цена — рост истории операций и копий
JSON-результатов; автоматическая очистка в этом блоке не реализована.

Если оператор добавит TTL, удалит ключ операции, Redis вытеснит его или история
потеряется при сбое, после этого защита данной операции пропадёт. Повтор с тем же
operation_id может создать новую запись с новым UUID, даже если старая ещё есть.
Не следует удалять историю только потому, что ответ уже отправлен. В дальнейшем
retention должен согласовываться с допустимым горизонтом retry или сохранять
долговечные маркеры; сейчас такого механизма нет. Текущий Compose без persistence
и тома теряет состояние при перезапуске; гарантий отсутствия потерь нет.

Для записей, созданных старой версией без operation_id, автоматически восстановить
историю действий нельзя. Backfill индексов не создаёт результаты идемпотентности.
Реализация не обеспечивает exactly-once доставку MAX, очередь или повтор внешних
вызовов. Идентичность входного события и идентичность бизнес-операции — разные
контракты; один запрос может содержать несколько operation_id.

## Проверки

Изменённые границы: `app/planner/operation.py` — идентификатор/fingerprint и
ошибка конфликта; три файла сервисов (`service.py`, `meeting_service.py`,
`reminder_service.py`) — проверка повтора до модели; три протокола
(`repository.py`, `meeting_repository.py`, `reminder_repository.py`) — контракт
метаданных и возврата сохранённой модели. Три `app/storage/redis_*.py`
репозитория вызывают общий `redis_operation.py` и проверяют результат;
`memory.py` поддерживает тот же контракт для локальных примеров. Модели и
бизнес-правила задач/встреч/напоминаний не менялись.

Прежние сервисные тесты обновлены для обязательного operation_id, тесты Redis —
для очистки также собственных ключей операций. README и backend-контракт
описывают новый вызов, документ списков фиксирует сохранение схемы индексов.

`tests/test_operation.py`: валидация, fingerprint и in-memory повторы.
`tests/test_redis_operations.py`: все три типа, новый клиент, изменение серверного
времени, эквивалентные смещения, конкурентные запросы, конфликт данных, изоляция
владельцев/типов, TTL `-1`, потеря ответа после commit, ошибки до записи и
повреждённая история. Тесты работают только в уникальном тестовом префиксе,
удаляют свои записи, индексы и результаты операций; `FLUSHDB` не используется.
