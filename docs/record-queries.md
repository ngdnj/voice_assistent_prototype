# Списки и простой поиск

`RecordQuery` в `app/planner/query.py` задаёт общий формат запроса, не объединяя
модели записей. Три сервиса предоставляют `list_tasks(query)`,
`list_meetings(query)`, `list_reminders(query)` и вызывают метод
`repository.list(query)`. Возвращаются списки своих моделей, пустая выдача — `[]`.
MAX, MCP и HTTP в этот контракт не входят.

## Владелец, период и порядок

`owner_id` обязателен и не может состоять из пробелов. Как и при создании,
он должен приходить от доверенного адаптера. Публичного режима «все владельцы»
нет. Идентификатор владельца не очищается по краям и не меняется автоматически.

| Тип | Фильтрация и сортировка по времени | Текст поиска |
| --- | --- | --- |
| Задача | `created_at`, поскольку срока у текущей модели нет | `title` |
| Встреча | `starts_at`; выбираются встречи, **начинающиеся** в периоде | `title` |
| Напоминание | `remind_at` | `text` |

`start_time` и `end_time` необязательны независимо друг от друга. Если заданы,
они должны быть aware datetime, проверяются существующим `to_utc` и переводятся
в UTC. Условия: `time >= start_time` и `time < end_time`. Две заданные границы
обязаны образовывать непустой период. Пересекающая период встреча, начавшаяся
до его начала, сюда не входит. Фильтр задач — дата создания, не срок выполнения.
Локальный день можно получить через `day_bounds_utc`, без разбора естественного языка.

Порядок всегда восходящий: `(поле времени, UUID)`. Микросекунды сохраняются,
UUID обеспечивает дополнительный порядок при одинаковом времени. `limit` —
целое число от 1 до 100, по умолчанию 50. `offset` — целое от 0 до 10000,
по умолчанию 0. Пустая страница допустима. Это offset-пагинация без снимка:
конкурентные добавления между запросами страниц могут сдвинуть их границы.

## Поиск и его пределы

Без `query` выполняется обычная выборка. Заданный `query` очищается по краям,
должен содержать 1–200 символов после `casefold()`. Сопоставление — вхождение
этой подстроки в `title.casefold()` или `text.casefold()`. Оно учитывает регистр
Unicode, но не морфологию, смысл, опечатки или эквивалентность «е/ё».
Это не PostgreSQL FTS, не embeddings и не семантический поиск.

Текстовый поиск рассматривает максимум 1000 кандидатов **одного типа, владельца
и выбранного периода**. Redis возвращает максимум 1001 элемент индекса для
проверки лимита. Если кандидатов больше 1000, выдаётся `QueryTooBroadError`:
следует сузить период. Частичный ответ не возвращается, поиск не ограничивается
первой страницей. Сначала фильтруется текст, затем применяется `offset/limit`.
Обычная выборка без текста не ограничивается 1000 записями, но читает не более
одной запрошенной страницы. Большие offset ограничены из-за линейной стоимости
пропуска элементов в Redis. Размер отдельного текста исторически не ограничен
моделью, поэтому лимит кандидатов не является гарантией бюджета байтов/времени.

```python
from datetime import date
from app.planner.query import RecordQuery
from app.planner.time import day_bounds_utc

async def example(meeting_service):
    start, end = day_bounds_utc(date(2026, 10, 22), "Europe/Moscow")
    return await meeting_service.list_meetings(RecordQuery(
        owner_id="user-42", start_time=start, end_time=end,
        query="проект", limit=20, offset=0,
    ))
```

## Redis-индексы и запись

JSON-ключи и формат `v1` существующих записей сохранены. Для каждого типа и
владельца добавлен sorted set:

```text
it-gorky:v1:index:task:owner:<owner_id UTF-8 hex>
it-gorky:v1:index:meeting:owner:<owner_id UTF-8 hex>
it-gorky:v1:index:reminder:owner:<owner_id UTF-8 hex>
```

Hex-кодирование обратимо и не позволяет разделителям в owner_id смешивать
пространства ключей. Это не сокрытие личности. Элемент индекса:
`<UTC ISO 8601 с шестью знаками микросекунд и +00:00>|<UUID>`.
Все score равны нулю: лексикографический порядок точно соответствует времени
и UUID, без округления микросекунд в float score.

`app/storage/redis_index.py` содержит только инфраструктурные примитивы:
Lua-запись, ключи и чтение индекса. Каждый конкретный репозиторий сохраняет
свою сериализацию, модель и проверку владельца. Lua проверяет отсутствие записи
и допустимый тип индекса **до изменений**, затем выполняет `SET NX` и `ZADD`
атомарно относительно других клиентов. Конфликт UUID ничего не меняет,
в том числе не добавляет ID в индекс другого владельца. TTL нет ни у записей,
ни у индексов. Операции изменения/удаления моделей пока отсутствуют; прямые
записи JSON сторонними клиентами обходят контракт и запрещены для рабочего пути.

Пользовательский запрос использует только индекс своего владельца и типа,
`ZRANGEBYLEX` с ограничением и `MGET` выбранных JSON. `KEYS`, `SCAN` и обход
общего пространства ключей на этом пути отсутствуют. После чтения проверяются
владелец, UUID и совпадение индексного времени с моделью. Потерянная запись,
неверный тип индекса или несовпадение дают соответствующий `*StorageError`,
без возврата чужих данных. Пропавший целиком индекс неотличим от пустого:
он не восстанавливается скрытым сканированием.

Реализация рассчитана на один Redis, не Redis Cluster. Lua обеспечивает
атомарность выполнения, но не откат любых runtime-ошибок сервера и не
долговечность при сбоях. Прежние ограничения persistence/тома/backup сохраняются.
Используемые механизмы: [Lua Redis](https://redis.io/docs/latest/develop/programmability/eval-intro/),
[лексикографические диапазоны](https://redis.io/docs/latest/commands/zrangebylex/).

Создания через прикладной сервис теперь дополнительно сохраняют результат
`operation_id` тем же атомарным Lua-вызовом. Схема и чтение индексов остаются
прежними; прямой add без метаданных сохраняет прежний скрипт записи и индекса.
Подробности — [idempotency.md](idempotency.md).

## Уже существующие записи: отдельный backfill

**Перед использованием списков на данных предыдущей версии необходимо один раз
построить индексы.** `get` по известному UUID продолжает работать и до backfill.
JSON не меняется, старые записи не удаляются. Вызовы прежней версии приложения
на время миграции нужно остановить, чтобы они не создавали записи без индексов.

```bash
uv run --locked --env-file .env python -m app.storage.reindex
# Для изолированного пространства:
uv run --locked --env-file .env python -m app.storage.reindex --key-prefix it-gorky-test
```

Это явно запускаемая административная команда, не часть запроса пользователя.
Она использует `SCAN` с шаблоном JSON-ключей каждого типа (Redis всё равно
проходит пространство ключей), валидирует записи и атомарно добавляет индекс
при условии, что прочитанный JSON не изменился. Повторный запуск безопасен:
один элемент не дублируется. Счётчик отражает обработанные записи, не только
новые элементы. Повреждение останавливает команду с ошибкой; уже построенные
индексы остаются, после исправления данных запуск повторяется. Команда делает
backfill, не ремонтирует произвольно изменённые/удалённые чужим кодом индексы.
В общих окружениях запуск миграции согласуется отдельно; автоматически она
не выполняется.

Проверки: `tests/test_record_query.py`, `tests/test_redis_queries.py`.
Интеграционные включаются `RUN_REDIS_INTEGRATION=1`; проверяют все три типа,
границы до микросекунды, одинаковое время, страницы, поиск, лимит кандидатов,
ошибку до записи при повреждённом индексе, конфликты и backfill старых JSON.
