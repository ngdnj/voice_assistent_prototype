# Локальный MAX-бот с настоящим backend

Ветка `origin/bot` подключена в рабочее дерево без merge-коммита. Сохранены её
MAX-клиент, парсер событий, ограничения аудио, Redis gate и тесты. DemoBackend
заменён адаптером `app/agent/bot_backend.py`.

Путь текста:

```text
MAX long polling → parse_update → BotService → AgentBackend → Assistant
  → MCP HTTP с доверенными заголовками → planner → PostgreSQL
  → результат инструмента → текст агента → MaxClient → MAX
```

BotService передаёт доверенного владельца из MAX, чат и время первого приёма.
AgentBackend сохраняет эти значения: job_id становится operation_id хода,
request_id используется для логов. Повтор Backend.answer с тем же запросом
воспроизводит прежний ход. Модель не устанавливает владельца и action_id.

## Что подготовить

`.env` находится в корне, исключён из Git. Не заменяйте файл, уже содержащий ключи.
Заполните локально:

```dotenv
MAX_BOT_TOKEN=
# Во время первого живого прогона — ID выделенного чата, не ID пользователя.
MAX_TEST_CHAT_ID=
MAX_DEFAULT_TIMEZONE=Europe/Moscow

GIGACHAT_CREDENTIALS=
GIGACHAT_SCOPE=GIGACHAT_API_PERS
GIGACHAT_MODEL=GigaChat-2-Max
GIGACHAT_BASE_URL=https://api.giga.chat/v1/
GIGACHAT_VERIFY_SSL=true
GIGACHAT_CA_BUNDLE_FILE=
MAX_CA_BUNDLE_FILE=

MCP_SERVICE_TOKEN=
MCP_URL=http://127.0.0.1:8001/mcp
```

Ключ GigaChat — Authorization Key без `Basic `; Client ID/Secret отдельно не нужны.
Scope должен соответствовать проекту ключа. MAX_BOT_TOKEN — отдельный токен бота MAX,
он не совпадает с ключом GigaChat. MCP_SERVICE_TOKEN — самостоятельно созданный секрет
не короче 32 символов, одинаковый у MCP и бота. Пример генерации: `openssl rand -hex 32`.

Для нового подключения GigaChat официальный целевой URL — `https://api.giga.chat`,
SDK получает base_url с `/v1/`. Авторизация пока использует
`ngw.devices.sberbank.ru:9443`; это отдельное исходящее соединение.
[Официальная авторизация GigaChat](https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/gigachat-api).

Если требуется российский CA, сохраните официальный PEM в игнорируемом `certs/`
и укажите путь. Проверку TLS не отключать. В текущей локальной настройке загружен
официальный корневой сертификат с
`https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt`.
MAX-клиент добавляет его к стандартным доверенным CA.

## Запуск с Docker Compose

Терминал 1, из корня:

```bash
uv sync --locked
docker compose up -d --wait postgres redis
uv run --locked --env-file .env alembic upgrade head
uv run --locked --env-file .env python -m app.mcp_server
```

Терминал 2:

```bash
uv run --locked --env-file .env python -m app.bot polling --text-only
```

`--text-only` не загружает GigaAM и не требует FFmpeg/torch для проверки текста.
Без него сохраняется прежняя ASR-граница MAX-компонента. Облачные вызовы GigaChat
могут расходовать пакет/бюджет. Не запускайте несколько polling-процессов для одного бота.

Бот должен быть без активного webhook. Проверить без изменения подписок:

```bash
uv run --locked --env-file .env python -m app.bot subscriptions
```

Если webhook уже используется другим разработчиком, сначала согласуйте переключение;
код не удаляет подписку автоматически.
Запуск polling при активном webhook завершается с событием
`polling_blocked_by_webhook`, вместо молчаливого ожидания сообщений в неверном режиме.

## Текущий запуск без Docker в этой среде

Здесь Docker отсутствует; для локальной проверки запущены собранные PostgreSQL 18.6
и Redis 7.4.2. PostgreSQL на 5433 хранит данные в игнорируемом `data/postgres`,
Redis слушает 6379; MCP — 8001. Пароли взяты из `.env`, не из документа.
PID MCP — `data/mcp.pid`, PID Redis — `data/redis.pid`, журналы — в `data/`.
Эта ручная сборка использует бинарники из `/tmp`; стандартный воспроизводимый путь
для другого компьютера — Compose выше. Не запускайте Compose на уже занятых портах.

После завершения проверки локальные процессы можно остановить:

```bash
kill -TERM "$(cat data/mcp.pid)"
/tmp/redis-7.4.2/src/redis-cli -p 6379 shutdown nosave
/tmp/it-gorky-test-services/pg/bin/pg_ctl -D data/postgres -m fast stop
```

Каталог PostgreSQL не удаляется. Redis пока без persistence, как в Compose;
перезапуск может потерять историю, планы и дедупликацию. Jobs/outbox ещё нет.

## Живая проверка и границы

Укажите MAX_TEST_CHAT_ID, запустите бота и отправьте из этого чата:

1. «Создай задачу подготовить демотест на завтра».
2. «Найди задачу про демотест».
3. «Что у меня завтра?».
4. «Встреча с Иваном завтра» — ожидается вопрос о времени.
5. «В 16:00» — ожидается создание встречи.
6. «Завтра встреча с часу до пяти по обсуждению хакатона» — создание на 13:00–17:00.
7. «Перенеси обсуждение хакатона на послезавтра в три часа дня» — та же встреча на 15:00–19:00.

Ответ, уточнение и ошибка заменяют «Принял запрос…», используя ID этого сообщения.
Ограничения и fallback: [перенос и время словами](meeting-reschedule.md),
[контракт MAX](../app/bot/INTEGRATION.md). После обновления выполнить миграции и
перезапустить MCP и бота, чтобы оба процесса увидели четвёртый инструмент.

Повтор доставки того же MAX-события не должен создавать вторую запись.
Новый отправленный пользователем текст, даже совпадающий с прежним, — новое событие
и новое действие; это не проверка дедупликации. Повтор answer(request) проверяется
отдельно с неизменным job_id/reference_time.

При MAX_TEST_CHAT_ID остальные чаты игнорируются **до** статусов и backend.
При пустом значении бот обслуживает все разрешённые MAX-события по обычным правилам.
Чтобы узнать ID, можно отдельно прочитать тестовое событие через GET /updates;
не запускайте второй потребитель параллельно работающему боту. Токен и полный
ответ API не выводите в логи.

Ctrl+C/SIGTERM прерывает long poll, прекращает приём, даёт активной работе до 10 секунд,
затем отменяет оставшееся. Сначала завершаются задания/снятие блокировок, затем закрываются
Redis, MAX/ASR и использованный GigaChat SDK client. Незавершённое действие не становится
успешным ответом. При падении процесса in-process работа может потеряться: это ограничение
ручного демо, не замена будущим jobs/outbox и dispatcher.

Обычный NAT не мешает исходящему long polling и запросам к моделям. Для webhook нужен
публичный HTTPS или туннель/VPS. Long polling здесь только для разработки/тестов,
как предусмотрено [MAX](https://dev.max.ru/docs-api/methods/GET/updates).

## Что проверено и что зависит от доступов

Автотесты используют реальный Redis, PostgreSQL и MCP HTTP, реальные MAX parser/client,
но подменяют внешнюю сеть MAX и ответы LLM. Они проходят создание, поиск, период,
уточнение встречи, повтор события, передачу job_id, ограничения чата и завершение работы.
Тесты не отправляют сообщений реальным пользователям и не расходуют облачную модель.

Живой smoke возможен только при настроенном MAX_BOT_TOKEN, выделенном тестовом чате
и доступной авторизации GigaChat. Отсутствие HTTP-ответа от auth endpoint — не проверка
валидности Authorization Key; не заменяйте ключ и не отключайте TLS из-за таймаута.
